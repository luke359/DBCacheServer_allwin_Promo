## 4. 文件定位與引用原則

- 本文件只定義實作組織方式、工作順序、整合步驟及完成標準，不重新定義業務規則。
- 名詞、列舉值、欄位語意及計算式以 PCS-01 為準。
- Schema、唯一索引、Transaction(交易)邊界與 Row Lock(資料列鎖)以 PCS-02 為準。
- Repository(儲存庫)、Adapter(轉接器)與 `MysqlAcess` 擴充契約以 PCS-03 為準。
- 公開 API(Application Programming Interface，應用程式介面)、Request(請求)、Result(結果)與 DTO(Data Transfer Object，資料傳輸物件)契約以 PCS-04 為準。
- 錯誤碼、重試與一致性規則以 PCS-05 為準。
- 測試案例、驗收條件與完成門檻以 PCS-06 為準。
- 若本文件的類別或檔案名稱與既有 Repository 命名規則衝突，可只調整名稱與實體路徑，不得合併分層責任或反轉第 7 節依賴方向；對照結果須記錄於第 22 節。
- 若實作時發現文件互相矛盾或缺少重要規則，必須先建立 Decision Log(決策紀錄)，修訂具有該規則所有權的上游文件並補測試；不得只改本文件或由實作者自行建立新業務語意。

## 5. 實作範圍與非目標

### 5.1 第一版必須交付

- PCS-01 的領域列舉、模型、Activity Snapshot(活動設定快照)版本 1 與 2、狀態不變條件及純計算元件。
- PCS-04 的同步 `IPromotionCoreService`、所有 Request、Result、DTO、輸入驗證及十二個公開方法。
- PCS-02 的五張資料表、完整索引、外鍵、Migration(資料庫移轉)及 Schema 驗證。
- PCS-03 的 `MysqlAcess` V2 型別化參數、交易 Context、查詢模型、資料存取例外分類及核心專用 MySQL Adapter。
- PCS-05 的錯誤映射、完整交易重試、Commit Outcome Unknown(提交結果不明)查證、結構化日誌及必要 Metric(指標)。
- DBCache 對 EventId、BonusTaskId、Wallet Instruction(錢包指令)、每局去重及每日維護的整合。
- PCS-06 全部 Unit Test(單元測試)、Contract Test(契約測試)、Integration Test(整合測試)及 Concurrency Test(併發測試)。
- Feature Flag(功能開關)、健康檢查、部署演練、回復程序及必要維運說明。

### 5.2 第一版非目標

- 不改成非同步 API，不導入 ORM(Object-Relational Mapping，物件關聯映射)，不替換既有 `MysqlAcess` 連線元件。
- 不在核心資料庫新增 Transactional Outbox(交易寄件匣)、遊戲局冪等表、維護執行表或第二套 Wallet Operation(錢包操作)表。
- 不由核心服務負責身份驗證、代理商規則、遊戲允許清單、押注上限執行、遊戲取消／退款或 H5gSet 活動編輯畫面。
- 不實體刪除 PromotionActivity、PromotionTriggerEvent、EligibilityEntry 或 PromotionBonusStatus；只依 PCS-02 清理超過 90 日的 PromotionBonusHistory。
- 不自動修復非法資料、長期 `Closing` 狀態或 `OutcomeUnknown`；此類情況必須停止相關流程並查證。
- 不處理企劃已接受的 Bonus Wallet 歸零套利風險，也不新增未經確認的風控規則。

範圍外需求若會改變資料語意、冪等性或交易邊界，必須先修改 PCS-01～PCS-06，不能以實作細節方式偷渡。

### 6.1 目標目錄

第一版以 C# 10、.NET 6 建立下列目標結構。若程式碼實際併入另一個 Repository，須在開始實作前把下列邏輯專案一對一映射至實際路徑。

```text

Directory.Packages.props
src/
  Promotion.Core.Contracts/

  Promotion.Data.MySql/
tests/
  Promotion.Core.UnitTests/
  Promotion.Core.ContractTests/
  Promotion.Data.MySql.IntegrationTests/
  Promotion.Core.ConcurrencyTests/
  Promotion.ArchitectureTests/
database/
  migrations/
  verification/
docs/
  decisions/
```

| 專案 | Target Framework | Root Namespace | 責任 |
|---|---|---|---|
| `Promotion.Core.Contracts` | `net6.0` | `Promotion.Core.Contracts` | 公開 Facade、Request、Result、DTO、公開列舉及委派 |
| `Promotion.Core` | `net6.0` | `Promotion.Core` | 領域模型、資料存取抽象、Validator、Calculator、流程協調、重試與錯誤映射 |

- `Directory.Build.props` 固定 `TargetFramework=net6.0`、`LangVersion=10.0`、`Nullable=enable`、`ImplicitUsings=enable`、`TreatWarningsAsErrors=true` 及 Deterministic Build(確定性建置)。
- `Directory.Packages.props` 集中管理正式與測試套件版本；各專案產生的 `packages.lock.json` 均納入版本控制，Continuous Integration(CI，持續整合)使用 Locked Mode(鎖定模式)還原。
- 測試框架只使用 xUnit、Microsoft.NET.Test.Sdk 及選配的 coverlet.collector；第一版不導入第三方斷言套件。
- 測試與正式 Adapter 必須使用同一 MySQL Driver(驅動程式)及版本；不得只在測試專案改用另一個 Provider。
- 所有原始碼、SQL、JSON 範例與設定範本使用 UTF-8；秘密值不得進入 Repository。

## 7. 分層、依賴方向與元件責任

### 7.1 允許的依賴

```text
DBCacheServer
    ├──> Promotion.Core.Contracts
    ├──> Promotion.Core                 只限組合根建立實作
    └──> Promotion.Data.MySql           只限組合根建立 Adapter

Promotion.Data.MySql ──> Promotion.Core ──> Promotion.Core.Contracts

Tests ──> 各自的受測專案
```

- `Promotion.Core.Contracts` 不參考任何其他本方案專案、MySQL Provider 或 Host 類別。
- `Promotion.Core` 只依賴 Contracts、.NET Base Class Library(基礎類別庫)及核准的 Logging Abstraction(日誌抽象)；不得參考 `MysqlAcess`、MySQL Provider 或 DBCache。
- `Promotion.Data.MySql` 實作 Core 的 `IPromotionDataStore` 與 `IPromotionDataTransaction`，可參考 `MysqlAcess`；Core 不反向參考 Adapter。
- `DBCacheServer/Promotion/PromotionCoreHost.cs` 的業務呼叫程式只依賴 `IPromotionCoreService`；只有組合根可直接看見 `PromotionCoreService`、`PromotionMySqlDataStore` 與連線建立細節。
- Test Fixture(測試夾具)不得被正式專案參考。

### 7.2 禁止依賴與架構 Gate(關卡)

- Core 不得出現 SQL、表名、欄名、Connection、Transaction、資料列 Dictionary 或 `MysqlAcess` 型別。
- Adapter 不得決定 Bonus、流水、Converted Amount、活動生效或狀態轉換等業務規則。
- Contracts 不得暴露可變領域物件、資料庫型別或例外訊息。
- Host 不得直接讀寫五張核心專用資料表，也不得直接呼叫 Repository 以繞過 Facade。
- `Promotion.ArchitectureTests` 必須實作 PCS-06 `ARC-001`：解析專案／組件參考並斷言 `Promotion.Core` 未參考 `MysqlAcess`、MySQL Provider 或 `Promotion.Data.MySql`；同時檢查正式專案沒有反向參考任何 Tests 專案。

## 9. 設定、初始化與 Dependency Injection(相依性注入)

### 9.1 設定來源與啟動驗證

| 設定／相依物件 | 來源 | 啟動規則 |
|---|---|---|
| MySQL 連線資訊 | Host Secret Store(秘密儲存區)或既有安全設定 | 不得寫入檔案、日誌或 Metric；建立 Adapter 前驗證可取得 |
| `BusinessDayCutover` | Host 版本化設定 | `00:00:00` 至小於 `24:00:00`，精度到秒；啟動後不可熱更新 |
| `BalanceConvertFormula` | DBCache 既有公式實作的同步委派 | 必填、決定性、無副作用；不得執行 I/O；啟動後不得更換委派實例 |
| `ILocalClock` | 正式 System Local Clock；測試 FixedLocalClock | 必須回傳 Local 或 Unspecified，不得回傳 UTC |
| `IGuidProvider` | 正式 Guid Provider；測試 SequenceGuidProvider | 產生小寫 `D` 格式字串 |
| Logger | Host 結構化 Logger | 依第 15 節遮罩；不得記錄 Connection String 或完整 Snapshot |
| `IRetryDelay`、`IJitterSource` | 正式同步 Delay／安全隨機來源；測試 Recording 實作 | Backoff 期間不得持有 Transaction、Connection 或玩家 Row Lock |
| Feature Flag | Host 版本化動態設定 | 只控制路由，不改變核心業務規則；Active Task 不可中途切回舊流程 |

正式設定的鍵名可沿用 Host 慣例，但部署清單必須能一對一對照上述項目。秘密值與一般設定分離管理。

### 9.2 生命週期

- `IPromotionCoreService`、初始化狀態、`IPromotionDataStore` 與正式 Clock 在單一 DBCache 程序中各使用 Singleton(單例)；Facade 初始化欄位必須使用執行緒安全的一次性發布。
- 單例 Data Store 可持有 `MysqlAcess`；已核准的 V2 每次呼叫使用獨立 Connection，單次 Transaction 內所有 Command 共用該 Connection／Transaction，不依賴舊 API 的共用 Mutex。
- `IPromotionDataTransaction` 與 `MysqlTransactionContext` 只在一次 `ExecuteInTransaction` 委派內有效，不註冊於容器、不快取、不跨執行緒。
- Request、Result、DTO、領域模型及 Calculator 結果不保存為 Singleton 可變狀態。
- 若現有 Host 未使用 Microsoft Dependency Injection(相依性注入)，可由組合根手動建構，但生命週期與依賴方向不變。

### 9.3 啟動順序

1. 驗證目標 MySQL 版本、Migration 狀態、連線安全設定及必要 Host 能力。
2. 建立 `MysqlAcess` V2、`PromotionMySqlDataStore`、Core 相依物件與 Facade。
3. 使用固定 `BusinessDayCutover` 與同一 `BalanceConvertFormula` 委派實例呼叫 `Initialize`。
4. 只有 `Initialize` 成功且 Schema 驗證通過時，Readiness 才可為 Ready(就緒)。
5. 啟動失敗時保持 Feature Flag 關閉，不得以預設切換時間、空公式或略過 Schema 驗證繼續。

每個 Request 若未提供 CorrelationId，Core 產生新的小寫 Guid 字串；同一次公開 API 的內部嘗試與結果必須沿用同一值。Host 外層重試應沿用原 CorrelationId，並另記 Host Attempt。

## 11. Schema 與 Migration 實作指引

### 11.1 版本與檔案

- 實作前由 DEC-001 固定正式環境 MySQL Major／Minor、Provider 版本及 `sql_mode`；CI 與發布候選版使用相同 Major／Minor。
- 第一版 Migration 命名為 `V001__create_promotion_core_tables.sql`；驗證腳本使用 `V001__verify_promotion_core_schema.sql`。後續修正只可新增 `V002` 以上版本，不覆寫已部署檔案。兩張獎勵表的正式更名由 `V003__rename_promotion_bonus_tables.sql` 處理；每日首登／首儲日期欄位由 `V004__bonus_status_daily_trigger_days.sql` 新增；活動封存狀態由 `V005__promotion_activity_status.sql` 新增。
- Migration 執行器必須永久記錄版本、檔案 SHA-256、開始／完成時間及結果。相同版本且 Hash 一致時跳過；版本相同但 Hash 不同時立即失敗。
- MySQL DDL 可能隱含 Commit，Migration 不得假設五張表能由單一 Transaction 原子回復。

### 11.2 建立與驗證順序

依外鍵相依順序建立：

1. `PromotionActivity`。
2. `PromotionTriggerEvent`。
3. `EligibilityEntry`。
4. `PromotionBonusStatus`。
5. `PromotionBonusHistory`。

每張表的 DDL、索引及外鍵完全採 PCS-02 第 6 節。完成後由 `information_schema` 驗證：

- Engine 為 InnoDB，Character Set 為 `utf8mb4`，Collation 為 `utf8mb4_bin`。
- 欄位型別、長度、精度、NULL、Default、Auto Increment 與主鍵一致。
- 所有 `UK_`、`IX_`、`FK_` 名稱、欄位順序與唯一性一致。
- EventId、BonusTaskId、ExclusiveGroup 實測區分大小寫。
- 目標玩家主檔的 UserUID 型別與核心 `BIGINT` 完全相容；不相容時停止部署，不做隱式轉型。

### 11.3 部署前檢查、失敗與回復

- 套用前保存 Schema Dump(結構備份)，確認執行帳號有必要 DDL 權限、剩餘空間與備份可還原。
- 正式首次上線的五張表應不存在；若已存在任一同名物件，先執行驗證腳本。完全一致才可納管，不一致必須停止並產生差異報告。
- 部分 DDL 失敗時不得盲目重跑整份檔案；先依 `information_schema` 確認已建立物件，再以新的受審修復 Migration 向前修正。
- 尚未寫入正式資料且 Feature Flag 未開啟時，可使用事先審核的反向順序腳本移除本次全新物件：PromotionBonusHistory → PromotionBonusStatus → EligibilityEntry → PromotionTriggerEvent → PromotionActivity。
- 一旦已有任何正式資料，不得 Drop Table 或回滾 Schema；回復方式是保留相容 Schema、關閉新資格／領取入口、回退程式並完成資料與錢包對帳。

## 12. MysqlAcess 擴充與 Adapter 實作指引

### 12.1 `MysqlAcess` V2

- 完整實作 PCS-03 的 `ExecuteParameterizedTransaction<T>`、`SelectParameterizedV2`、`DeleteParameterizedV2` 與 `MysqlTransactionContext`。
- 值只接受 PCS-03 第 13.1 節型別白名單；`null` 綁定 `DBNull.Value`，decimal 不經 double 或地區字串中轉。
- Table、Field、Order、Operator、LockMode 由固定白名單／enum 產生；所有 Value 使用 Provider Parameter。
- Update／Delete 的 Where 不可空；Limit 大於 0 且 Core 批次上限為 1000；`In` 必須是非空集合。
- `ForUpdate` 只允許有效交易 Context；非交易 Select 指定鎖模式立即失敗。
- Transaction Context 的所有 Command 明確設定同一 Connection 與 Transaction；完成 Commit、Rollback 或 Dispose 後，任何再呼叫都須丟出明確的失效例外。
- 交易開始後禁止單一 Command 自動重連／重送，禁止巢狀 Transaction，禁止 action 內混用舊 API 或非交易 V2 API。

### 12.2 Adapter

- 每個查詢明列欄位，不使用 `SELECT *`；表、欄位與 Constraint 名稱集中於 `PromotionTableMetadata`。
- 寫入 Snapshot 時使用固定 UTF-8 JSON 設定，新任務寫入版本 2；讀取時先驗證 SnapshotVersion，再按版本驗證欄位與 PCS-01 不變條件。版本 1 的計算方式固定為 `BonusOnly`，不得改寫既有快照。
- DateOnly 寫入 DATE；DateTime 以本地語意寫入 DATETIME(6) 並保留微秒；Guid 使用小寫 `D` 格式 CHAR(36)。
- Database NULL 保持 `null`；不得沿用舊 API 的空字串替代行為。
- 未知 enum、溢位、缺欄、非法 JSON、非法欄位組合或 decimal 經 double 造成不一致，一律轉為 `PromotionDataErrorKind.DataCorruption`。
- Duplicate Key 優先取得實際 ConstraintName；無法辨識時不得從例外文字猜測，回 `DataIntegrityConflict`。
- Insert 必須以 `LastInsertedId` 回傳完整 `EligibilityEntry`／`BonusHistory`；不得暫填 0。
- 修改 `MysqlAcess` 後同步更新 [MysqlAcess 使用說明](./MysqlAcess使用說明.md)，並保證舊 API 的既有簽名與行為不變。

### 12.3 明確禁止

- 禁止 SQL 字串插值、串接條件、把參數值寫回可執行 SQL 或以自由文字傳入運算子。
- 禁止 Core 直接建立 `MysqlSelectCommand` 或知道 ConstraintName。
- 禁止 Adapter 捕捉所有例外後回傳空集合、0、預設 enum 或 `null`。
- 禁止以 SQLite、Mock Provider 或同一連線模擬 MySQL Transaction 與 Row Lock 的整合測試。

## 13. 核心業務流程實作指引

所有 API 先建立／驗證 CorrelationId，完成可在交易前判斷的輸入驗證，再取得一次操作時間。業務錯誤轉 Result，不把資料存取例外洩漏給 Host。

| API／流程 | 實作順序與共用元件 |
|---|---|
| `Initialize` | 驗證 Cutover 與公式；以執行緒安全方式只設定一次；相同值／同一委派重呼回 `WasAlreadyInitialized`；不開 DB Transaction、不試呼公式 |
| `CreateEligibility` | `BusinessDayCalculator` → 完整交易重試 → 鎖 PromotionBonusStatus → 查 EventId → 重播／衝突判斷 → 插入 Event → 每日首登／首儲比對最近 Business Day；事件日期小於等於保存日期時成功回空 Entries，較晚時更新日期 → 活動篩選 → 依 ActivityUID 插入 Entries → Commit 後映射結果；零 Entry 仍成功 |
| `GetAvailablePromotions` | 驗證 QueryTime → 計算 Business Day → 非交易查詢 Entry、Activity 與 Status → 以目前活動計算預估值 → EligibilityEntryId 遞增；不得把預估值當領取承諾 |
| `ClaimPromotion` | 完整交易重試 → 鎖 PromotionBonusStatus → 鎖 Entry → 驗證玩家／日期／狀態／任務／上限 → 讀目前 Activity → 建 Snapshot → 計算金額 → 產生 BonusTaskId → Claimed／Status／Excluded 全部同交易 → Commit 後建立 `CreditBonusWallet` 指令 |
| `GetBonusTaskStatus` | 非交易讀 Status → 驗證不變條件與 Snapshot → 即時計算 Remaining；`Closing` 或非法欄位組合不得視為無任務 |
| `AccumulateWager` | 完整交易重試只適用 Commit 前明確 Rollback → 鎖 Status → 驗證 Expected ID → 依 Snapshot 計算有效流水 → 一律 Save；未達標回 InProgress、達標回 ReadyToClose，不建立 History 或 Wallet 指令；Commit 開始後結果不明立即停止重送 |
| `CloseWagerCompletedBonusTask` | 鎖 Status → 驗證 Expected ID 與目前流水已達標 → 已結案則由 History 重播 → 以 WagerCompleted 呼叫 `BonusTaskCloser`，Balance 公式使用 Host 傳入的達標局資料 → Commit 後回結果 |
| `CloseDepletedBonusTask` | 鎖 Status → 驗證 Expected ID 與餘額為 0 → 已結案則由 History 重播 → 依 PCS-04 判斷 WagerCompleted 或 BonusDepleted → `BonusTaskCloser` → Commit 後回結果 |
| `AbandonBonusTask` | 鎖 Status → 驗證 Expected ID → 已結案則重播 → 以 PlayerAbandoned 結案 → Commit 後回 `ClearBonusWallet` |
| `RunDailyMaintenance` | 固定一次 CurrentBusinessDay／HistoryCutoffTime → 資格逾期 → 任務逾期 → 歷史清理；不清除每日首登／首儲日期；Keyset Pagination；每位玩家獨立交易；失敗隔離；指令依 UserUID／BonusTaskId 排序並以 OperationKey 去重 |
| `GetBonusHistory` | 驗證時間範圍與分頁 → 非交易查詢 → ClosedAt、BonusHistoryId 降冪 → 映射唯讀 DTO；已合法清除資料不保證存在 |

### 13.1 四種結案共用路徑

`BonusTaskCloser` 必須在呼叫端已取得玩家鎖的同一 Transaction 中執行：

1. 先查相同 BonusTaskId 的 History；內容一致則還原既有成功，內容衝突則停止。
2. 將 `TaskState` 設為暫時性 `Closing`，不得在 Commit 後殘留。
3. 只有 `WagerCompleted` 計算 Converted Amount；公式失敗使整筆交易 Rollback。
4. 插入完整不可變 History，再依 PCS-01 第 14 節重置 Status。
5. Commit 成功或查證既有成功後，才依 CloseReason 產生固定順序的 Wallet Instructions。

Wallet Instruction、DTO 與日誌均由已提交的領域結果產生；不得在 Transaction 內呼叫 DBCache Wallet。

## 14. Transaction、Row Lock 與併發實作指引

### 14.1 責任分界

| 元件 | 責任 |
|---|---|
| `MysqlAcess` V2 | 開始／Commit／Rollback／Dispose 實體 Transaction；確保同 Connection；分類 Provider 錯誤 |
| `PromotionMySqlDataStore` | 將單次 Transaction 暴露為 `IPromotionDataTransaction`；不自行重送業務 action |
| `PromotionCoreService`／`PromotionRetryExecutor` | 決定完整業務交易是否可重試、建立新 Context、重新讀取及保留同一 Request／CorrelationId |
| `CommitOutcomeVerifier` | 使用新連線與業務識別碼查證成功、明確未提交或無法判定 |
| DBCache Host | 收到 RetryableFailure 後重呼完整 API；OutcomeUnknown 不自動重送；Wallet 依 OperationKey 重試 |

### 14.2 固定鎖定順序

所有異動嚴格遵守：PromotionBonusStatus(UserUID 遞增) → PromotionTriggerEvent(EventId 遞增) → EligibilityEntry(EligibilityEntryId 遞增) → PromotionActivity(ActivityUID 遞增) → PromotionBonusHistory(BonusTaskId)。

- 玩家 Status 不存在時先嘗試新增空白列；主鍵競爭後重新查詢並 `FOR UPDATE`。
- 同玩家排除多筆資格時依 EligibilityEntryId 遞增，不可由未排序集合產生更新順序。
- 取得玩家鎖前的候選查詢不構成寫入承諾；進入交易後重新驗證全部狀態。
- 不同 UserUID 必須可由不同 Data Store／Connection 並行；不得用全域業務 Mutex 取代 Row Lock。

### 14.3 Commit 與錯誤路徑

- `action` 正常完成後才 Commit；Commit 完成前不建立可執行 Wallet 結果。
- `action` 例外時明確 Rollback；Rollback 失敗需保留原始失敗並記錄次要錯誤。
- Deadlock、Lock Wait Timeout 與確認未提交的 Connection Failure 由 Core 最多嘗試三次完整交易；每次建立新 Context、重新取得鎖與重新讀取。
- `UK_PromotionBonusStatus_BonusTaskId` 碰撞使整筆領取 Rollback，換新 Guid 後重做，總嘗試仍受三次上限。
- 其他 Duplicate Key 必須依 PCS-05 Constraint 對照查回既有事實；內容不一致不得視為成功。
- 進入 Commit 後連線中斷，不在原 Context 重做 action；關閉壞連線後交由 `CommitOutcomeVerifier`。
- `AccumulateWager` 進入 Commit 後結果不明一律回 `OutcomeUnknown / CommitOutcomeUnknown`，不得以目前流水推測本局是否已處理。

Backoff 必須在 Transaction 與 V2 專用 Connection 均已釋放後執行。核心與 Host 的時間、jitter 及上限分別完全採 PCS-05 第 13、18 節。

## 15. 錯誤、重試、日誌與可觀測性

### 15.1 錯誤轉換

- 輸入 Validator 依 PCS-05 回傳對應的 1xxx，歷史範圍錯誤則回 `InvalidHistoryRange`（5002）；不開交易、不呼叫公式、不產生 Wallet 指令。
- 業務狀態拒絕回 `Rejected`；正常拒絕不以 Exception(例外)控制流程。
- `PromotionDataErrorKind` 只由 Adapter 產生，Core 依 PCS-05 第 12 節轉換；Host 不解析 Provider Code 或 Exception Message。
- `DataCorruption`、`Unexpected` 與未知 Constraint 不重試；分別回固定 PermanentFailure，建立告警所需事件。
- `OutcomeUnknown` 的 `IsRetryable` 固定 false，且不得附帶可直接執行的新 Wallet Instruction。
- `PromotionResultFactory` 使用資料驅動對照表固定 Kind、ErrorCode、IsRetryable；ERR-001 必須涵蓋全部 enum 值。

### 15.2 結構化日誌

每次公開 API 使用一個 Scope(範圍)，至少記錄：

- API 名稱、DLL 版本、SnapshotVersion、CorrelationId、開始／結束本地時間、耗時。
- Result Kind、PromotionErrorCode、IsRetryable、Core Attempt、Host Attempt。
- 遮罩後 UserUID、EventId、EligibilityEntryId、BonusTaskId。
- Transaction 階段、Commit 狀態、查證分支及 Provider 分類；只在 Deadlock／Lock Wait 記錄必要 MySQL 錯誤碼。
- Wallet Action、OperationKey Hash、Amount 與順序；維護另記固定界線、批次及成功／失敗計數。

禁止記錄連線字串、密碼、Token、錢包憑證、完整 Snapshot JSON、完整 Balance Convert Context、未遮罩玩家資料或把參數組回可執行 SQL。

### 15.3 Metric 與告警

Metric 名稱可依既有平台前綴調整，但語意及低基數 Label(標籤)固定：

| Metric | 類型 | Label |
|---|---|---|
| `promotion_core_api_total` | Counter | API、ResultKind、ErrorCode |
| `promotion_core_api_duration_ms` | Histogram | API、ResultKind |
| `promotion_core_transaction_retry_total` | Counter | API、DataErrorKind、Attempt |
| `promotion_core_commit_outcome_unknown_total` | Counter | API、VerifyResult |
| `promotion_core_wallet_instruction_total` | Counter | Action、SaveResult |
| `promotion_core_maintenance_item_total` | Counter | Stage、Result |
| `promotion_core_data_corruption_total` | Counter | Model／Table |

不得以 UserUID、EventId、BonusTaskId、CorrelationId 或 OperationKey 作 Metric Label。以下事件必須接入告警：DataCorruption、UnexpectedError、任何 OutcomeUnknown、Balance 公式重試耗盡、Wallet 指令無法可靠保存／超過處理時限、維護 PartialSucceeded、Migration／Readiness 失敗。數量與時間門檻由 DEC-005 在部署前固定。

## 16. DBCache 整合指引

### 16.1 整合前置條件

DBCache 必須先具備可持久保存 Wallet Instruction 的儲存機制；至少保存 OperationKey、Action、UserUID、BonusTaskId、Amount、順序、狀態、嘗試次數、建立／更新時間及最後錯誤分類，並以 OperationKey 建立唯一限制。實際表或既有服務由 DEC-003 決定，不可新增到核心五張表。

若無法保證「先可靠保存，再執行錢包」，不得開啟領取、達標結案、主動放棄或跨日結案的新流程。

### 16.2 呼叫與識別碼

- EventId 由 Host 在接收來源事件時產生並可靠保存；所有重試沿用相同值。核心不接受 Host 因 Timeout 另產新 EventId。
- BonusTaskId 只由 Core 產生；Host 由成功 Result 保存並在後續每次任務異動傳入 `ExpectedBonusTaskId`，不得自行產生或替換。
- CorrelationId 用於追蹤，不具冪等性；不可取代 EventId、BonusTaskId 或 OperationKey。
- `AccumulateWager` 前由 DBCache 以既有遊戲紀錄保證每局最終資料只送一次。核心 Result 成功、失敗或不明均須與該局紀錄一起保存。
- `AccumulateWager` 回 `ReadyToClose` 後，Host 必須停止該任務後續局並以同一達標局的餘額、下注、派彩及時間呼叫 `CloseWagerCompletedBonusTask`；累計成功但結案失敗時只重試結案 API，不得重送流水。
- 每日維護重試必須沿用原 ExecutionTime；同一執行期間 CurrentBusinessDay 與 HistoryCutoffTime 不變。

### 16.3 Wallet 指令處理

```text
呼叫 Core
  ↓ 成功或 PartialSucceeded 且含指令
在 DBCache Transaction 內保存全部指令與順序
  ↓ 保存成功
依 OperationKey 執行第一個 Pending 指令
  ↓ 成功後標記完成
執行同 BonusTaskId 的下一個指令
```

- `CreditMainWallet` 只能在同任務的 `ClearBonusWallet` 已完成後執行。
- 指令失敗只重試該指令，不重呼已成功的 Core 業務操作，也不回復 Core 狀態。
- Claim 的 `CreditBonusWallet` 完成前不得允許玩家開始任務；結案必要指令完成前維持既有提款／任務限制。
- 相同 OperationKey 重送只可讀取既有狀態或重試未完成操作，不可建立第二筆入帳。
- 對帳補執行必須使用原 BonusTaskId 與 Action 形成的 OperationKey；禁止直接修改核心表。

### 16.4 Result 處理

| Core Result | Host 行動 |
|---|---|
| `Succeeded` | 若含 Wallet 指令，先可靠保存全部指令再依序派發；不含指令時依正常成功流程處理 |
| `PartialSucceeded` | 保存統計、Failures 與成功項目的指令；需重跑維護時沿用原 ExecutionTime，不回復已成功項目 |
| `Rejected` | 顯示／記錄業務拒絕；不自動重試 |
| `RetryableFailure` | 依 PCS-05 Host Backoff 重呼完整相同 Request，最多指定次數 |
| `PermanentFailure` | 停止、記錄並依 ErrorCode 修正設定、資料或程式 |
| `OutcomeUnknown` | 凍結相關後續流程、保存原 Request 與局資料、建立對帳案件；禁止盲目重送 |

### 16.5 新舊流程切換

- Feature Flag 至少支援 Disabled、Pilot Allowlist(試行允許清單)、Enabled 三態；玩家一旦由新核心成功處理任何寫入，後續優惠操作固定走新流程，路由標記的保存方式由 DEC-004 決定。Active Task 結案及 Wallet 指令完成前絕對不可切回舊流程。
- 緊急關閉只停止尚未進入新流程玩家的新事件與新領取；已由新核心建立 Event、Eligibility 或 Active Task 的玩家，其查詢、領取、流水、結案、Wallet 重試與對帳仍須由新流程完成。
- Pilot 不得對同一事件同時寫入新舊流程；若需 Shadow(影子)比較，只能比較無副作用的讀取／純計算結果。
- 維護排程預設同一分片只允許一個主動 Runner 以降低衝突，但正確性仍須能承受重複或同時執行。

- 測試結束先執行 PCS-06 第 19.3 節殘留檢查，再刪除專用資料庫；失敗時先輸出遮罩診斷。
- Concurrency Test 的兩端不得共用 Connection、Data Store 或 Facade；V2 不使用舊 API 的程序內 Mutex。若共用同一 `MysqlAcess` 實例，仍須證明各端使用獨立 V2 Connection。

## 18. 部署、升級、回復與相容性

### 18.1 部署順序

1. 完成第 22 節所有阻擋正式部署的決策、備份與部署前檢查。
2. 在 Feature Flag Disabled 下套用向前相容的 Schema，執行 V001 驗證。
3. 部署含 `MysqlAcess` V2、Adapter 與 Core 的 DBCache 程式，但保持新業務入口關閉。
4. 驗證 Process Health(程序健康)、Initialization、DB Readiness、Metric、日誌遮罩及 Wallet 指令儲存。
5. 啟用內部測試帳號，再啟用 Pilot Allowlist；觀察至少完整一個 Business Day 與一次每日維護。
6. 確認無未解 OutcomeUnknown、Wallet Pending、資料損毀或維護失敗後，分批擴大至 Enabled。

### 18.2 相容範圍

- Schema 先行部署且只新增物件；舊版 DBCache 不讀寫新表，因此應不受影響。
- 同一玩家不得同時由兩個版本處理優惠；一旦新核心成功寫入 Event、Eligibility 或 Task，路由需持續黏著新流程，至少到所有 Active Task 與 Wallet 指令完成，後續解除條件由 DEC-004 明確定義。
- Contracts 的 enum 數值、Result 不變條件、SnapshotVersion 1 與 OperationKey 格式視為發布後相容契約，不可原地改義。
- 滾動部署期間，新舊實例必須使用相同 BusinessDayCutover、公式版本與資料庫 Schema；任一不一致時停止擴大流量。

### 18.3 健康檢查

- Liveness(存活)只驗證程序與工作執行緒可回應，不因短暫 DB 問題重啟迴圈。
- Readiness 驗證 Core 已 Initialize、Migration 版本／Hash 正確、MySQL 可建立查詢連線、必要 Wallet Store 可用；不呼叫 Balance 公式或寫入業務資料。
- 每日維護 Runner、Wallet Dispatcher 與 Reconciliation Queue(對帳佇列)各有獨立健康狀態，不以 API Ready 掩蓋背景處理停止。

### 18.4 回復條件與方式

遇到 DataCorruption、持續 OutcomeUnknown、重複錢包入帳、唯一鍵／外鍵違反、Migration 差異、未遮罩敏感日誌或維護大量失敗時，立即停止擴大並進入回復程序。

- 尚無新流程資料：關閉旗標、回退程式；經確認無資料後才可使用審核過的反向 Schema 腳本。
- 已有 Eligibility 或 Task：停止新事件與領取，但保留新版本處理既有任務、Wallet 重試與對帳；不得把 Active Task 交給舊流程。
- 已有 History／Wallet 操作：保留 Schema，不做資料庫時間點還原覆蓋其他玩家的新資料；以業務識別碼逐案對帳。
- 禁止以手動刪列、改 Status、重建 BonusTaskId 或重放 `AccumulateWager` 作為一般回復手段。

## 20. Definition of Done(完成定義)

第一版完成必須同時符合：

- 所有正式專案可在 Locked Mode 下 Restore，Release Build 零警告、零錯誤。
- 公開 API、enum 數值、DTO、SnapshotVersion 及錯誤碼與 PCS-01、PCS-04、PCS-05 完全一致，無重複契約。
- `Promotion.ArchitectureTests` 證明 Core 不依賴 `MysqlAcess`、MySQL Provider、DBCache 或 Tests。
- 五張表可由空資料庫套用 V001，Schema／索引／外鍵／Collation 驗證全過；Migration Hash 已鎖定。
- `MysqlAcess` V2 所有值參數化，Transaction Context 正確失效，交易內無單條 SQL 自動重送，使用說明已同步。
- Adapter 完成 PCS-01 全欄位映射與非法資料拒絕；未以預設值掩蓋資料損毀。
- PCS-06 全部必要 Unit、Contract、Integration、Concurrency、Architecture Test 通過，沒有 Skip／Ignore／空斷言。
- 主分支 50 回及夜間 500 回併發為零失敗、零重複任務、零重複 History、零部分交易殘留。
- Fault Injection 覆蓋 BeforeCommit、DuringCommit、AfterCommitBeforeReturn 及三種查證結果；`AccumulateWager` 結果不明未被重送。
- 所有 Wallet Instruction 先可靠保存再依 OperationKey 執行，順序與冪等性通過 WAL-001～WAL-013。
- 結構化日誌、Metric、Alert、遮罩及失敗診斷完成；輸出不含秘密、完整 Snapshot 或可執行 SQL。
- DBCache 聯調、全新環境部署、Pilot、每日維護、失敗注入及回復演練均有可追溯證據。
- PCS-01～PCS-07、`MysqlAcess` 使用說明、Migration、Runbook 與實際行為同步，所有已採用 Decision Log 已簽核。
