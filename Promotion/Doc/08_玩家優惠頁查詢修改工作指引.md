# PCS-08 玩家優惠頁查詢修改工作指引

## 1. 目的與範圍

本文件定義玩家進入優惠頁時，取得「代理商可見全部優惠」及玩家個別優惠狀態的修改工作。

已確認的責任分工如下：

- Host(宿主服務)負責代理商－活動授權，先取得玩家所屬代理商可見的 `ActivityUID` 清單。
- Promotion Core(優惠核心)負責依該清單讀取活動，並結合玩家資格、進行中任務及選用的當日完成紀錄。
- 前端不自行判斷領取資格或是否可按領取按鈕。

本次不在 Promotion Core 資料庫新增代理商欄位或代理商－活動對照表，也不變更既有領取、任務及結算交易流程。

## 2. 現況盤點

目前 `IPromotionCoreService` 已有下列分離式讀取 API(Application Programming Interface，應用程式介面)：

| 現有方法 | 可提供資料 | 不足處 |
|---|---|---|
| `GetAvailablePromotions` | 玩家當日可領的 `EligibilityEntry`、預估獎金與是否已有任務 | 不會回傳沒有資格的活動，也不接受代理商活動範圍 |
| `GetBonusTaskStatus` | 玩家唯一的執行中任務及進度 | 不會回傳全部活動 |
| `GetBonusHistory` | 指定期間的已結束任務歷史 | 是分頁查詢，非優惠頁主清單 |
| `GetActivitiesByTriggerType`（資料存取層） | 依觸發類型與活動 ID 清單讀取活動 | 不支援依 ID 清單讀取完整活動清單，也不是公開核心 API |

因此不能僅靠既有 `GetAvailablePromotions` 完成畫面；若由 Host 逐一組裝，會使活動篩選、按鈕可用性及狀態優先序分散在 Host。

## 3. 目標設計

新增一個唯讀的 Promotion Core 公開方法：

```csharp
GetPlayerPromotionPage(GetPlayerPromotionPageRequest request)
```

Request(請求) 至少包含：

```text
UserUID
QueryTime
VisibleActivityUIDs      // Host 已依代理商授權算出的活動範圍
IncludeTodayCompleted    // 是否附帶「本活動日已完成」區塊
CorrelationId
```

Result(結果) 至少包含：

```text
UserUID
BusinessDay
HasAnyActiveBonusTask
ActiveTask               // null 或唯一一筆執行中任務
Activities               // 每個可見活動一筆，供主優惠清單使用
TodayCompletedItems      // 僅 IncludeTodayCompleted = true 時回傳
```

每個 `Activities` 項目至少包含：

```text
ActivityUID、ActivityInfo、活動規則畫面欄位
EligibilityEntryId       // null 表示目前沒有可領資格
CanClaim                 // EligibilityEntryId != null
HasActiveTask            // 此活動即為玩家目前執行中的活動
ClaimButtonEnabled       // CanClaim && !HasAnyActiveBonusTask
ActiveTaskProgress       // HasActiveTask 時的目前／需求流水
```

`TodayCompletedItems` 沿用或等價於既有 `BonusHistoryDto`，篩選條件為 `UserUID` 與 `BusinessDay`；此欄位僅供獨立區塊顯示，不影響主清單的 `CanClaim` 與按鈕判斷。

## 4. 畫面狀態規則

| 使用者可見狀態 | 判斷 | UI 行為 |
|---|---|---|
| 已領、正在執行任務 | `HasActiveTask = true` | 顯示特殊符號與任務進度；不顯示領取按鈕 |
| 可領且可立即領取 | `CanClaim = true` 且 `ClaimButtonEnabled = true` | 點亮 icon，啟用領取按鈕 |
| 可領但暫不可領取 | `CanClaim = true` 且 `ClaimButtonEnabled = false` | 點亮 icon，停用領取按鈕；原因為已有另一個執行中任務 |
| 不可領 | `CanClaim = false` | 不顯示領取按鈕，仍顯示活動資訊 |

注意：玩家有其他活動任務執行中時，已產生的 `EligibilityEntry.Status = Available` 仍是「可領資格已成立」，不得改判為「不可領」。按鈕是否可按應使用 `ClaimButtonEnabled`。

## 5. 查詢與資料存取修改

### 5.1 資料存取介面

在 `IPromotionDataStore` 與 MySQL Adapter(資料庫轉接器)新增批次讀取能力：

```csharp
IReadOnlyList<PromotionActivity> GetActivitiesByIds(
    IReadOnlyCollection<long> activityUids);
```

目的為一次取得 Host 授權範圍內的全部活動；方法不得自行判斷代理商授權。

另外新增依玩家、活動日與活動範圍取得可用資格的批次查詢，避免優惠頁逐活動查詢：

```csharp
IReadOnlyList<EligibilityEntry> GetAvailableEligibilityEntries(
    long userUid, DateOnly businessDay, IReadOnlyCollection<long> activityUids);
```

既有單參數版本可保留給舊 API 使用，或以新版本實作它。查詢需使用 `UserUID`、`BusinessDay`、`Status` 索引，並在記憶體或 SQL 中以 `ActivityUID` 限縮授權範圍。

歷史區塊僅在 `IncludeTodayCompleted = true` 時，呼叫既有 `GetBonusHistory` 等價查詢；不可在未啟用時讀取歷史資料。

### 5.2 核心組裝規則

1. 驗證 `UserUID`、`QueryTime`、活動 ID 清單數量與重複值。
2. 由 `QueryTime` 計算 `BusinessDay`。
3. 批次讀取可見活動、可用資格與玩家 `PromotionBonusStatus`。
4. 以 `ActivityUID` 合併成每活動一筆的主清單資料；活動排序應使用穩定規則（暫定 `ActivityUID ASC`，若已有後台排序欄位則改用該欄位）。
5. 若 `PromotionBonusStatus.TaskState = InProgress`，只將相同 `ActivityUID` 標記為 `HasActiveTask`，但所有具有可用資格的活動都必須依規則計算 `ClaimButtonEnabled`。
6. `IncludeTodayCompleted = true` 時，讀取該 `BusinessDay` 的完成歷史並獨立回傳。

此方法為唯讀操作，不使用 Row Lock(資料列鎖)，不需交易；領取時仍以既有 `ClaimPromotion` 的交易檢查為最終依據，避免查詢到領取之間的競態條件。

## 6. Host 修改工作

1. 在玩家登入後或請求優惠頁前，依既有代理商階層／活動設定查出 `VisibleActivityUIDs`。
2. 將該清單原樣傳給 `GetPlayerPromotionPage`；不可讓前端傳入活動範圍。
3. 將核心回覆映射為既有 WebSocket 或 SignalR 前端協定。
4. 領取指令一律帶回核心提供的 `EligibilityEntryId`，並保留既有 `ClaimPromotion` 的錯誤碼處理。

## 7. 合約、測試與驗收

### 7.1 契約測試

- 空白活動範圍回傳空主清單，不應查出其他活動。
- 重複活動 ID 不產生重複活動項目。
- 未授權活動即使玩家有 `EligibilityEntry` 也不可出現在結果。
- 活動主清單永遠每個 `ActivityUID` 一筆。

### 7.2 核心單元測試

- 沒有資格：活動存在、`CanClaim = false`、無領取按鈕。
- 有資格且無任務：`CanClaim = true`、`ClaimButtonEnabled = true`。
- 有資格且其他活動任務進行中：`CanClaim = true`、`ClaimButtonEnabled = false`。
- 本活動任務進行中：`HasActiveTask = true`，正確回傳流水進度。
- 當日完成歷史開關關閉時，不讀取歷史；開啟時僅回傳該活動日歷史。
- 頁面查詢結果與隨後 `ClaimPromotion` 的最終交易檢查不一致時，仍以 `ClaimPromotion` 結果為準。

### 7.3 整合測試

- 使用實際 MySQL 索引驗證活動範圍、可用資格與任務狀態的合併結果。
- 驗證 V003 後的實際表名：`PromotionBonusStatus`、`PromotionBonusHistory`。
- 驗證大量授權活動 ID 時的上限與 SQL 參數數量；上限數值須與既有 `GetActivitiesByTriggerType` 的 1000 筆限制一致，或在實作前正式調整。

## 8. 實作順序

1. 確認第 9 節待決策事項並更新 PCS-04 API 規格。
2. 增加 Contracts 的 Request、Result、DTO 與驗證規則。
3. 擴充資料存取介面、MySQL 查詢與整合測試。
4. 實作 `PromotionCoreService.GetPlayerPromotionPage` 與核心單元／契約測試。
5. Host 串接代理商活動授權來源與前端回覆協定。
6. 以測試帳號驗收四種主清單狀態；若保留歷史區塊，再驗收當日完成清單。

## 9. 待審核決策事項

以下項目會改變公開契約或畫面語意，實作前必須確認：

1. **活動清單範圍**：只顯示 `ActivityStatus = Active` 的代理商授權活動，還是也顯示 `Archived`、未開始或已結束活動？
2. **活動排序**：目前資料表沒有排序欄位。使用 `ActivityUID ASC`、後台新增排序欄位，或由 Host 授權資料提供順序？
3. **不可領原因**：第一版僅回傳 `CanClaim = false`，還是須精準呈現未達儲值門檻、日期不符、今日額度已滿等原因？目前未符合條件的觸發事件不會建立 `EligibilityEntry`，若要精準原因須另行設計條件評估資料來源。
4. **今日已完成區塊**：預設關閉並以 `IncludeTodayCompleted` 控制，或第一版直接不實作、待產品確認後另案加入？
5. **可用資格多筆**：同活動同日若因多個事件產生多筆 `EligibilityEntry`，主清單是否只呈現一筆且領取最新一筆，或必須讓玩家選擇／逐筆顯示？目前建議主清單一活動一筆，但需明訂選取規則。

---

## 10. 非目標

- 不在核心建立或維護代理商活動授權資料。
- 不把優惠頁查詢視為領取授權；領取仍必須呼叫 `ClaimPromotion`。
- 不因本功能調整任務結算、錢包指令或既有歷史保留期限。
