# 優惠活動核心服務企劃

## 1. 文件資訊

| 項目 | 內容 |
|---|---|

| 文件狀態 | 第一版業務規則已確認 |

## 2. 企劃目標

核心服務負責管理玩家從取得優惠資格、領取 Bonus(紅利)、執行 Bonus Task(紅利任務)，直到任務結案與保留歷史紀錄的完整生命週期。

第一版以能正確支援基本優惠流程為優先，主要目標如下：

1. 統一管理優惠活動設定與生效條件。
2. 根據觸發事件建立玩家可領取的優惠資格。
3. 允許多個優惠資格並存，但限制每位玩家同一時間只能進行一個 Bonus Task。
4. 管理領取次數、活動疊加、互斥群組及活動日到期規則。
5. 累計有效流水，判斷任務是否達標並計算 Converted Amount(解鎖金)。
6. 支援達標、紅利用盡、主動放棄及逾期失效四種結案方式。
7. 保存結案歷史 90 日，並提供每日維護功能。

第一版不預先設計尚未提出的進階活動模型，後續再依實際營運需求擴充。

## 3. 企劃範圍

### 3.1 核心服務負責事項

- 保存及讀取優惠活動設定。
- 判斷活動是否於指定 Business Day(活動日)生效。
- 接收觸發事件並建立 Eligibility Entry(可領活動項目)。
- 查詢玩家目前可領取的優惠。
- 驗證優惠是否可以領取。
- 計算應派發的 Bonus 與 Required Wager Amount(目標流水量)。
- 領取時保存活動設定快照，供該次 Bonus Task 後續計算使用。
- 建立、更新及結束 Bonus Task。
- 保存並重複使用 Bonus Status(玩家優惠活動總狀態)。
- 根據有效遊戲資料累計 Current Wager Amount(已累計流水量)。
- 判斷任務是否完成，並計算 Converted Amount。
- 套用不可疊加及 Exclusive Group(優惠互斥群組)規則。
- 保存 Bonus History(活動歷史紀錄)90 日。
- 執行活動日切換、逾期結案及歷史資料清理。

### 3.2 不在核心服務範圍內

- 玩家身份驗證。
- Main Wallet(主錢包)與 Bonus Wallet(優惠錢包)的實際加款、扣款、清空及提款控制。
- 儲值、金流及一般遊戲紀錄的處理。
- 判斷代理商是否參加特定活動。
- 維護代理商可執行解鎖任務的遊戲清單。
- 判斷遊戲是否可用於優惠任務。
- 攔截超過活動押注上限的投注。
- 遊戲限制、注單取消及退款。
- 玩家進行 Bonus Task 期間的主錢包提款限制。
- 玩家進行 Bonus Task 期間，後續儲值是否應排除於優惠領取條件的判斷。
- H5gSet(活動設定後台)的輸入範圍及預設值驗證。

上述功能由 DBCache、GameServer(遊戲伺服器)、H5gSet 或其他上層系統負責。核心服務只接收上層已篩選完成的資料並回傳業務處理結果。

## 4. 系統角色與責任邊界

| 系統／元件 | 主要責任 | 與核心服務的協作 |
|---|---|---|
| DBCache | 身份驗證、金流、錢包、遊戲紀錄及資料庫相關業務 | 作為 Host(主程式)載入核心服務；傳入活動日切換時間；為觸發事件提供全域唯一 EventId(事件識別碼)；確保每局最終遊戲資料只送入一次；通知觸發事件、錢包歸零及每日維護；依核心服務結果處理錢包、重試及錯誤處理 |
| H5gSet | 優惠活動設定與設定值驗證 | 建立或更新核心服務使用的活動設定 |
| GameServer | 遊戲執行、遊戲限制與押注上限檢查 | 將已通過遊戲資格及押注限制檢查的遊戲資料交由 DBCache 處理 |
| 核心服務 | 優惠資格、任務、流水、結案及歷史紀錄 | 回傳可領活動、任務狀態、結案結果及需要清空 Bonus Wallet 的玩家清單 |

代理商可決定參與哪些優惠活動，以及哪些遊戲可執行解鎖任務；相關判斷由 Host 處理。`PromotionActivity.GameServerList` 保存優惠可玩遊戲列表，核心服務僅提供 Host 依活動 UID 查詢完整字串，不解析或判斷內容。

## 5. 名詞定義

| 名詞 | 定義 |
|---|---|
| Main Wallet(主錢包) | 保存玩家儲值本金與一般遊戲贏得之真錢，可提款 |
| Bonus Wallet(優惠錢包) | 保存平台派發的 Bonus，用於執行 Bonus Task，不可提款 |
| Bonus(紅利) | 存放於 Bonus Wallet 的鎖定資金，不可直接提款 |
| Bonus Task(紅利任務) | 玩家領取 Bonus 後，累計有效流水直到結案的過程 |
| Converted Amount(解鎖金) | Bonus Task 達標後，由 DBCache 發放至 Main Wallet 的可提款金額 |
| Convert Type(解鎖金類型) | 決定達標後 Converted Amount 的計算方式，與 Bonus 派發方式無關 |
| Fixed Convert(固定解鎖額) | 達標後無條件發放設定的固定解鎖金全額 |
| Balance Convert(依餘額解鎖) | 達標後以外部注入公式計算 Converted Amount；設定上限非空時套用上限 |
| Bonus Status(玩家優惠活動總狀態) | 每位玩家唯一且永久保留的優惠總狀態；建立後重複使用，不刪除 |
| Eligibility Entry(可領活動項目) | 觸發事件完成後，為符合條件的活動建立之當日暫時領取資格 |
| Bonus History(活動歷史紀錄) | Bonus Task 結案後保存 90 日的紀錄 |
| Required Wager Amount(目標流水量) | 完成 Bonus Task 所需累計的有效投注總額 |
| Current Wager Amount(已累計流水量) | Bonus Task 目前已累計的有效投注額 |
| Remaining Wager Amount(剩餘流水量) | `RequiredWagerAmount - CurrentWagerAmount`；顯示時不得小於零 |
| Business Day(活動日) | 從 Host 傳入的每日切換時間起，至下一次切換時間前的活動週期 |
| Exclusive Group(優惠互斥群組) | 同一群組內只能成功領取一個優惠的活動集合 |

## 6. 共通規則

### 6.1 活動日與時間

- 預設活動日切換時間為每日 08:00。
- 實際切換時間由 Host 定義，並於核心服務啟動時傳入。
- 活動日切換時間只用於判斷 Business Day。
- 歷史紀錄建立時間、更新時間及其他一般時間欄位使用系統本地時間。
- 例如切換時間為 08:00，則 2026-09-15 的 Business Day 範圍為 2026-09-15 08:00:00 起，至 2026-09-16 08:00:00 前。

### 6.2 數值與精度

本企劃所稱「金額、流水及計算結果使用 `decimal`」，是指實際執行優惠任務時產生或參與運算的數值，不代表所有活動設定欄位都必須保存為 `decimal`。

數值型別分為以下三類：

| 類別 | 代表欄位 | C# 型別 | 建議 MySQL 型別 | 規則 |
|---|---|---|---|---|
| 整數活動設定 | 固定金額、優惠最高金額、儲值百分比、最低儲值金額、洗碼量、押注上限、固定解鎖金、依餘額解鎖金上限、領取次數 | `int` 或 `int?` | `INT` | 可為空欄位以 `null` 表示未設定或無限制；有值時只允許整數 |
| 小數活動設定 | 押注流水比例 | `decimal` | `DECIMAL` | 設定範圍允許小數，因此設定值本身使用 `decimal` |
| 任務金額與計算結果 | 合格儲值金額、Bonus、Required Wager Amount、Current Wager Amount、每局有效流水、Converted Amount | `decimal` | 小數位數為 4 的 `DECIMAL` | 運算及保存均保留最多 4 位小數 |

計算時，整數活動設定應先精確轉換成 `decimal`，再與其他金額進行運算。`int` 轉換成 `decimal` 不會產生精度遺失。

```csharp
int fixedAmount = activity.FixedAmount;
decimal bonus = fixedAmount;
```

百分比設定以整數百分數保存，例如 `30` 表示 `30%`。參與計算時必須使用 `decimal` 除法轉為比例值，不得使用整數除法。

```csharp
int percentage = activity.DepositPercentage;
decimal rate = percentage / 100m;
decimal bonus = qualifiedDepositAmount * rate;
```

其餘精度規則如下：

- 核心服務執行期的實際金額、流水及計算結果一律使用 `decimal`。
- 所有需要限制精度的計算結果均直接截斷至小數第 4 位，不得四捨五入。
- 整數活動設定值本身不需要進行四位小數截斷。
- 為相容舊系統，外部介面可使用 `double`；資料進入核心服務後必須立即轉換成 `decimal`。
- 外部公式回傳的 `double` 必須先排除 `NaN`、正負無限值及負數，再轉換成 `decimal` 並截斷至小數第 4 位。

### 6.3 命名規則

資料表名稱、資料表欄位名稱、程式變數及方法名稱統一使用 Pascal Case(帕斯卡命名法)。

### 6.4 資料庫存取架構

核心服務設計及實作資料庫存取方法時，必須參考 [MysqlAcess 使用說明](./MysqlAcess使用說明.md)。若使用說明與 `DBCacheServer/MysqlAcess.cs` 原始碼不一致，以原始碼為準，並同步更新使用說明。

資料庫存取採用下列分層：

```text
核心業務邏輯
    ↓
核心專用資料存取介面
    ↓
MysqlAcess 參數化 API
    ↓
MySQL
```

- 核心服務必須自行定義符合優惠領域的資料存取介面，例如 Eligibility Entry、Bonus Status、Bonus Task、領取交易及每日維護等操作；實際介面與方法名稱於 API 規格階段定義。
- 資料存取實作應包裝 `MysqlAcess`，不得讓核心業務邏輯直接操作表名、欄位名稱或 `Dictionary<string, string>`。
- 核心服務不另行建立資料庫連線元件或重寫一套通用資料庫存取層；底層沿用並依需求擴充 `MysqlAcess`。
- 新功能預設使用 Parameterized Query(參數化查詢)，簡單新增、更新及查詢應分別使用 `InsertParameterized`、`UpdateParameterized` 及 `SelectParameterized`。
- 不得因現有參數化 API 能力不足，改用舊版 SQL 字串拼接方法規避限制。需要 Transaction(交易)、Row Lock(資料列鎖)、參數化刪除、日期範圍、排序、分頁或其他複雜條件時，應先擴充 `MysqlAcess` 的參數化能力。
- 領取優惠涉及玩家鎖定、資格更新、建立 Bonus Task、增加領取次數及排除互斥資格，必須在同一資料庫交易中完成；任一步驟失敗時整筆回復。
- 多個 DBCache 程序或服務實例並存時，玩家鎖必須使用 MySQL 資料列鎖或具有同等跨程序效果的機制，不得以 `MysqlAcess` 的程序內 Mutex(互斥鎖)代替。
- `EventId + 活動 UID`、BonusTaskId 及其他不得重複的業務識別，必須建立資料庫唯一索引，作為自動重試及併發操作的最終防重機制。
- 傳入參數化 API 的數字及日期字串必須使用 `CultureInfo.InvariantCulture`；呼叫端必須遵守 `MysqlAcess` 對 `null`、日期格式、識別字及例外處理的規則。

## 7. 優惠活動設定

活動設定由 H5gSet 管理；輸入範圍及預設值驗證亦由 H5gSet 負責。核心服務依已驗證的設定執行業務規則。

| 設定項目 | 預設值 | 規則與用途 |
|---|---:|---|
| 活動 UID | `null` | 長整數；活動唯一序號，由時間值與衝突序號組成 |
| 活動資訊 | `null` | 最長 100 字元；顯示給玩家的名稱與說明 |
| 優惠類型 | 固定金額 | Bonus 派發方式：固定金額或儲值百分比；儲值百分比僅供 Bonus 派發金額計算，且僅能搭配每日首儲或儲值觸發類型 |
| 固定金額 | 10 | `1～100` 幣，整數；固定金額活動領取時派發的 Bonus |
| 優惠最高金額 | 10 | `1～100` 幣，整數；百分比 Bonus 的上限 |
| 儲值百分比 | 30 | `1～1000%`，整數；以該 Eligibility Entry 的合格儲值金額計算 Bonus |
| 最低儲值金額 | 10 | `10～1000` 幣，整數；免費活動不設定 |
| 洗碼量 | 30 | `1～100`，整數；用於計算 Required Wager Amount |
| 目標流水計算方式 | 1 | `1`：優惠 × 洗碼量；`2`：(儲金 + 優惠) × 洗碼量，沒有儲金時以 0 計 |
| 押注上限 | 5 | `NULL` 表示無限制；有值時為 `1～100` 幣整數，由 GameServer 執行限制 |
| 可玩遊戲列表 | `null` | 最長 500 字元；核心原樣提供 Host 查詢 |
| 押注流水比例 | 100 | `1.0～100.0%`；用於計算每局有效流水 |
| 解鎖金類型 | 固定 | 固定解鎖金或依餘額解鎖金 |
| 固定解鎖金 | 5 | `1～1000` 幣，整數；Fixed Convert 達標時發放的全額 |
| 依餘額解鎖金上限 | 150 | `NULL` 表示無限制；有值時為 `1～1000` 幣整數，是 Balance Convert 計算結果的上限 |
| 領取次數 | 1 | `1～99` 次，整數；每個 Business Day 成功領取本活動的次數上限 |
| 活動開始日期 | `null` | 只記錄日期；從該日活動切換時間起生效；`null` 表示不限開始日期 |
| 活動結束日期 | `null` | 只記錄日期；從該日活動切換時間起停止；結束日期不包含於活動期間；`null` 表示無限期 |
| 星期遮罩 | `0000000` | 由星期一至星期日；`1` 表示有效，`0` 表示無效；`0000000` 表示停用 |
| 活動狀態 | Active | `Active` 可依其他條件產生新資格；`Archived` 不再產生新資格，但既有有效資格仍可領取 |
| 觸發類型 | 每日首儲 | 註冊、每日首登入、每日首儲、儲值或免費活動 |
| 不可疊加 | `false` | 一般優惠預設允許疊加；控制不同 Eligibility Entry 是否會在成功領取後互相排除，不代表可同時進行多個 Bonus Task |
| 優惠互斥群組 | `null` | 同群組只能成功領取一個優惠；`null` 表示不屬於任何群組 |

### 7.1 活動生效條件

一個活動必須同時符合下列條件，才可於當次觸發事件中產生 Eligibility Entry：

1. 活動狀態為 `Active`。
2. 星期遮罩在目前 Business Day 所屬星期為有效。
3. 星期遮罩不為 `0000000`。
4. Business Day 不早於活動開始日期；未設定開始日期時不限制。
5. Business Day 早於活動結束日期；未設定結束日期時不限制。
6. 活動觸發類型與收到的觸發事件相符。
7. 儲值型事件符合最低儲值金額。
8. 玩家在本 Business Day 內成功領取本活動的次數尚未達上限。
9. 該活動已在 Host 提供的代理商可參加活動範圍內。

H5gSet 必須禁止「註冊」、「每日首登入」及「免費活動」搭配「儲值百分比」，避免 Eligibility Entry 缺少可用的合格儲值金額計算基數。

## 8. 玩家資料模型

本節定義業務概念，不限定實際資料表拆分方式。

### 8.1 Bonus Status

- 每位玩家僅有一份 Bonus Status。
- 第一次需要使用時建立，之後持續重複使用且永不刪除。
- 每次成功領取均建立唯一的 BonusTaskId(紅利任務識別碼)。
- 用於保存玩家目前是否有進行中的 Bonus Task，以及該任務的 BonusTaskId、活動、Bonus、流水、押注與結案計算所需狀態。
- 保存最近一次每日首登入與每日首儲事件所屬的 Business Day，作為跨程序一致的每日首次判斷；兩者互相獨立。
- 領取時必須保存該活動完整的設定快照。該 Bonus Task 的 Bonus、Required Wager Amount、押注限制、流水及 Converted Amount 等後續計算一律使用此快照，不受活動設定後續修改影響。
- Bonus Task 結案後，應先建立 Bonus History，再將本次任務相關欄位重置。
- 玩家識別及永久性總狀態保留；本次任務的活動 UID、金額、目標流水、已累計流水及其他暫時資料歸零或清空。
- 每日首登入／首儲日期不是任務暫時資料，結案及每日維護均保留；較晚 Business Day 以日期遞增自然恢復可觸發狀態，延遲舊日事件不得使日期倒退。

### 8.2 Eligibility Entry

- 以玩家、活動、Business Day 及 EventId 為主要識別範圍。
- 保存產生資格的 EventId、觸發類型、合格儲值金額、建立時間及有效狀態。
- 同一玩家可以同時持有多個有效 Eligibility Entry。
- 同一個 EventId 由 Host 保證全域唯一。核心服務對同一 EventId 的重送必須重複使用首次處理結果，不得重新篩選活動或重複建立 Eligibility Entry。
- 同一 EventId 對同一活動最多只能建立一筆 Eligibility Entry；一般觸發類型的不同 EventId 可在同一玩家、活動及 Business Day 下分別建立資格，但仍受領取次數上限限制。每日首登入／首儲同日第二個不同 EventId 只保存事件，不建立資格。
- Eligibility Entry 僅在建立時所屬的 Business Day 有效，不得延續至下一個 Business Day。
- 資格存在只代表可選擇領取，不代表已開始 Bonus Task。

Eligibility Entry 的狀態至少包含：

| 狀態 | 說明 |
|---|---|
| 可領取 | 尚未領取且仍在有效 Business Day 內 |
| 已領取 | 玩家已使用此資格成功建立 Bonus Task |
| 已排除 | 因不可疊加或 Exclusive Group 規則而失效 |
| 已逾期 | Business Day 切換時仍未領取 |

### 8.3 Bonus History

- 每次 Bonus Task 結束時建立一筆歷史紀錄。
- 至少應能識別 BonusTaskId、玩家、活動、Business Day、活動設定快照、Bonus、Required Wager Amount、Current Wager Amount、Converted Amount、結案方式及結案時間。
- 歷史紀錄保留 90 日。
- 核心服務負責於每日維護時刪除逾期歷史資料。

## 9. 優惠活動主要流程

### 9.1 建立可領資格

1. 玩家完成註冊、每日首登入、每日首儲、儲值或免費活動等觸發事件。
2. Host 完成核心服務範圍外的身份、代理商活動名單及事件前置判斷。
3. 核心服務取得全域唯一 EventId、觸發事件與必要資料。
4. 每日首登入／首儲事件先在玩家鎖內比對 Bonus Status 的最近觸發 Business Day；事件日期小於或等於保存日期時只保存本次 Trigger Event，成功回傳空資格。
5. 每日首次事件且 Business Day 晚於保存日期時，先更新對應日期，再依活動日期、星期遮罩、觸發類型、最低儲值金額及領取次數上限篩選活動。首儲日期以第一筆成功儲值為準，即使未達任何活動門檻仍會占用當日首儲。
6. 核心服務為每個符合條件的活動建立 Eligibility Entry，並以 EventId 與活動 UID 防止重複建立。
7. 玩家可於本 Business Day 內查詢並選擇其中一個優惠領取，也可暫不領取並進入一般遊戲。

若 Host 重送相同 EventId，核心服務須回傳首次處理產生的既有結果，不得因活動設定或玩家狀態已變更而重新計算該事件。

### 9.2 查詢可領優惠

核心服務只回傳目前狀態為可領取、尚未逾期且未被互斥規則排除的 Eligibility Entry。

若玩家已有進行中的 Bonus Task，既有 Eligibility Entry 可以保留至其原 Business Day 結束，但玩家在目前任務結案前不得領取另一個優惠。

### 9.3 領取優惠

核心服務開始領取流程前，必須先取得該玩家的排他鎖，並在同一資料庫交易內完成驗證及領取狀態寫入。同一玩家的兩個領取要求同時到達時，以先取得鎖者優先；後取得鎖者必須重新檢查玩家狀態。若系統存在多個 DBCache 程序或服務實例，必須依 6.4 節使用資料庫交易鎖或具有同等跨程序效果的機制，不得只使用程序內鎖。

取得鎖後，領取前須同時符合下列條件：

1. Eligibility Entry 屬於該玩家。
2. Eligibility Entry 仍在建立時所屬的 Business Day 內。
3. Eligibility Entry 狀態為可領取。
4. 玩家目前沒有進行中的 Bonus Task。
5. 該活動於本 Business Day 的成功領取次數尚未達上限。
6. 該資格未被不可疊加或 Exclusive Group 規則排除。

領取成功後：

1. 依活動的優惠類型計算 Bonus。
2. 計算 Required Wager Amount。
3. 產生唯一 BonusTaskId，並保存領取當下的完整活動設定快照。
4. 將 Eligibility Entry 標記為已領取。
5. 建立進行中的 Bonus Task 並更新 Bonus Status。
6. 將本次成功領取計入該活動於本 Business Day 的領取次數。
7. 套用不可疊加及 Exclusive Group 規則，排除其他不再可領取的資格。
8. 將 BonusTaskId 與 Bonus 派發資訊回傳 DBCache，由 DBCache 實際存入 Bonus Wallet。

只有完整領取成功才計入領取次數；失敗的領取嘗試不得消耗次數。

核心服務完成上述領取交易後，即視為核心領取成功。若 DBCache 派發 Bonus Wallet 失敗，核心服務不得回復 Eligibility Entry、Bonus Task、領取次數或互斥排除結果。DBCache 負責以相同 BonusTaskId 安全重試、避免重複入帳及執行錯誤處理；派發成功前，DBCache 不得允許玩家開始使用該 Bonus Task。

### 9.4 Bonus 計算

#### 固定金額

```text
Bonus = 固定金額
```

#### 儲值百分比

儲值百分比僅能用於每日首儲或儲值觸發的活動，並只用於計算本次應派發的 Bonus。

```text
原始 Bonus = Eligibility Entry 的合格儲值金額 × 儲值百分比
Bonus = Min(截斷至小數第 4 位的原始 Bonus, 優惠最高金額)
```

### 9.5 Required Wager Amount 計算

```text
計算方式 1：RequiredWagerAmount = 截斷至小數第 4 位(Bonus × 洗碼量)
計算方式 2：RequiredWagerAmount = 截斷至小數第 4 位((儲金 + Bonus) × 洗碼量)
```

「儲金」使用該 Eligibility Entry 的 `EligibleDepositAmount`；值為 `null` 時以 0 計。

新任務的 `CurrentWagerAmount` 為 0，`RemainingWagerAmount` 等於 `RequiredWagerAmount`。

## 10. 疊加與互斥規則

### 10.1 基本限制

- 玩家可同時持有多個 Eligibility Entry。
- 玩家同一時間最多只能有一個進行中的 Bonus Task。
- 「不可疊加」只控制資格是否會在其他不可疊加優惠領取後被排除，不允許同時進行多個 Bonus Task。

### 10.2 不可疊加活動

玩家成功領取一個「不可疊加 = `true`」的優惠後，其他尚未領取且同為「不可疊加 = `true`」的 Eligibility Entry 全部標記為已排除。

「不可疊加 = `false`」的 Eligibility Entry 不因上述規則自動失效，但仍須等目前 Bonus Task 結案後才能領取，且不得超過原 Business Day。

### 10.3 Exclusive Group

- 玩家成功領取屬於某個 Exclusive Group 的優惠後，同一群組內其他尚未領取的 Eligibility Entry 全部標記為已排除。
- 此規則不受「不可疊加」設定影響。
- 若同類型優惠只能擇一領取，應將這些活動設定為相同 Exclusive Group。
- `null` 表示不參與群組互斥。

不可疊加與 Exclusive Group 規則同時存在時，兩者均須套用；任一規則判定應排除的資格即失效。

## 11. 流水累計與任務達標

### 11.1 有效遊戲資料

- GameServer 與 DBCache 先完成代理商遊戲名單、遊戲限制、押注上限、重送、取消及退款等處理。
- DBCache 必須確保每局最終有效遊戲資料只送入核心服務一次；遊戲資料重送的識別與去重由 DBCache 負責。
- 核心服務只接收 DBCache 已篩選完成的最終有效遊戲資料，包括該局押分、得分、遊戲時間及該局結算後的 Bonus Wallet 餘額。
- 核心服務不再次判斷遊戲是否允許，也不處理取消或退款。
- Bonus Wallet 的遊戲扣款由 DBCache 負責。

### 11.2 每局有效流水

```text
本局有效流水 = 截斷至小數第 4 位(本局押注 × 押注流水比例)
CurrentWagerAmount = CurrentWagerAmount + 本局有效流水
RemainingWagerAmount = Max(RequiredWagerAmount - CurrentWagerAmount, 0)
```

核心服務完成計算後，將更新後的流水、剩餘流水及 Bonus Task 結果回傳 DBCache。核心服務不負責識別同一局資料是否已送入；DBCache 若重送同一局資料，視為 DBCache 的資料處理錯誤。

### 11.3 達標條件

```text
CurrentWagerAmount >= RequiredWagerAmount
```

達標後核心先保存流水並回傳 `ReadyToClose`，不立即結案。DBCache Host(主機端整合程式)停止該任務後續遊戲局，再呼叫獨立達標結案方法進入 Converted Amount 計算流程。超過目標的流水不另行產生額外獎勵。

## 12. Bonus Task 生命週期

| 狀態 | 說明 |
|---|---|
| 無進行中任務 | 玩家可領取任一有效且未被排除的 Eligibility Entry |
| 進行中 | 已領取 Bonus，正在累計有效流水；不可再領取其他優惠 |
| 結案處理中 | 已觸發結束條件，正在建立歷史與計算結案結果 |
| 已結案 | 已建立 Bonus History 並重置本次 Bonus Task 狀態 |

Bonus Task 有四種正式結案方式：

1. 完成目標流水量。
2. 輸光 Bonus。
3. 玩家主動放棄。
4. Business Day 切換時逾期失效。

### 12.1 完成目標流水量

1. `CurrentWagerAmount` 達到或超過 `RequiredWagerAmount`。
2. 累計方法只保存最新流水並回傳 `ReadyToClose`，不得建立 Bonus History 或重置 Bonus Status。
3. DBCache Host 以造成達標的同一局資料呼叫獨立達標結案方法。
4. 核心重新確認流水已達標，並依 Convert Type 計算 Converted Amount。
5. 成功建立 Bonus History，重置 Bonus Status 中本次任務資料。
6. 回傳結案結果，由 DBCache 在收到成功結果後清空 Bonus Wallet，並將 Converted Amount 發放至 Main Wallet。

### 12.2 輸光 Bonus

- Bonus Wallet 由 DBCache 管理。
- 當該局結算後 Bonus Wallet 歸零時，若該局須計流水，DBCache 先完成流水累計，再依累計結果呼叫達標結案或用盡結案；結案不得與流水累計合併在同一核心呼叫。
- 核心服務收到通知後，以「輸光 Bonus」建立 Bonus History 並結案。
- 核心服務不得自行查詢或判斷 Bonus Wallet 餘額。
- 此結案方式的 Converted Amount 為 0。

### 12.3 玩家主動放棄

- 玩家可在 Bonus Task 進行中主動放棄。
- 核心服務以「主動放棄」建立 Bonus History 並結案。
- 此結案方式的 Converted Amount 為 0。
- 核心服務回傳成功結案結果後，由 DBCache 清空 Bonus Wallet。

### 12.4 逾期失效

- Business Day 切換時，所有仍在進行中的 Bonus Task 以「逾期失效」結案。
- 核心服務必須先建立 Bonus History，再重置 Bonus Status 中的任務資料。
- 核心服務回傳需要清空 Bonus Wallet 的玩家清單，由 DBCache 將其 Bonus Wallet 歸零。
- 同一時間，前一 Business Day 尚未領取的 Eligibility Entry 全部標記為已逾期。

### 12.5 結案後處理

- 任務結案後，玩家本次優惠參與即告完成。
- 玩家恢復可提款狀態的實際控制由 Host 負責。
- 若仍有未失效且未被互斥規則排除的 Eligibility Entry，玩家可選擇領取另一個優惠。
- 新優惠能否領取仍以該 Eligibility Entry 原本的 Business Day 有效期限為準。

## 13. Converted Amount 計算

### 13.1 Fixed Convert

```text
ConvertedAmount = 固定解鎖金
```

- 達標後無條件發放設定的固定解鎖金全額。
- 固定解鎖金可以高於結案當下的 Bonus Wallet 餘額，也可以高於原始 Bonus。
- 此行為是刻意設計，不得再以錢包餘額或原始 Bonus 限縮。

### 13.2 Balance Convert

1. 核心服務將玩家 Bonus Status 的必要參考資料傳入外部注入公式。
2. 公式輸出為相容舊系統的 `double`。
3. 核心服務驗證輸出後轉為 `decimal`，並截斷至小數第 4 位。
4. 套用「依餘額解鎖金上限」。

```text
ConvertedAmount = 依餘額解鎖金上限為 NULL 時，使用截斷至小數第 4 位的公式結果；否則取該結果與上限的較小值
```

### 13.3 外部公式失敗

若公式發生下列任一情況，本次結案失敗：

- 拋出例外。
- 回傳 `NaN`。
- 回傳正無限或負無限值。
- 回傳負數。

失敗時必須：

1. 保留原 Bonus Task 與 Bonus Status，不得建立成功結案結果。
2. 不得重置流水及任務資料。
3. 不得發放 Converted Amount。
4. 將失敗結果回傳 DBCache，由 DBCache 記錄錯誤後重試。

## 14. 每日維護

DBCache 每個 Business Day 呼叫核心服務的維護方法一次。核心服務依序完成：

1. 找出前一 Business Day 尚未領取的 Eligibility Entry，標記為已逾期。
2. 找出已跨 Business Day 且仍在進行中的 Bonus Task。
3. 逐筆建立「逾期失效」Bonus History。
4. 成功建立歷史後，重置對應玩家 Bonus Status 的任務資料。
5. 回傳需要清空 Bonus Wallet 的玩家清單。
6. 刪除保存期限已超過 90 日的 Bonus History。

每日維護不清除 Bonus Status 的每日首登入／首儲日期；這兩個日期只供與事件所屬 Business Day 比對，排程延遲或失敗不得阻擋新活動日的首次事件。

DBCache 收到結果後，負責將清單內玩家的 Bonus Wallet 歸零。

單筆任務若未能成功寫入歷史，不得先清除該玩家的任務狀態；應回傳失敗供 DBCache 記錄並重試。

每日維護不要求 Host 提供 EventId，但核心服務的維護操作必須具備 Idempotency(冪等性)。同一 Business Day 的維護被重複呼叫或同時執行時，不得重複建立 Bonus History、重複重置 Bonus Status、重複變更 Eligibility Entry，或對歷史資料產生不同結果。核心服務應以資料目前狀態、BonusTaskId 及資料庫交易或唯一限制確保安全重複執行。

## 16. 第一版驗收情境

### 16.1 資格與領取

- 同一觸發事件符合多個活動時，能建立多個 Eligibility Entry。
- Host 重送相同 EventId 時，核心服務回傳首次處理結果，且不重複建立 Eligibility Entry。
- 一般觸發類型的不同 EventId 可在同一玩家、活動及 Business Day 下分別產生資格，並共同受當日領取次數上限限制；每日首登入／首儲同日僅第一次可產生資格。
- 註冊、每日首登入及免費活動不得設定為儲值百分比優惠。
- 玩家暫不領取時，可在同一 Business Day 內再次查詢並領取。
- 已有 Bonus Task 時，不得再領取另一個優惠。
- 領取成功後正確增加該活動於當日的成功領取次數。
- 領取失敗不增加領取次數。
- 達到當日領取次數上限後，不得再次領取同一活動。
- Business Day 切換後，未領取資格均不可再領取。
- 同一玩家同時提出兩個領取要求時，僅先取得玩家鎖且通過驗證者成功。
- 領取成功後修改活動設定，既有 Bonus Task 仍使用領取時保存的設定快照。
- DBCache 派發 Bonus Wallet 失敗時，核心領取結果維持不變，並可使用相同 BonusTaskId 安全重試而不重複入帳。

### 16.2 疊加與互斥

- 領取不可疊加優惠後，其他不可疊加資格均被排除。
- 領取某 Exclusive Group 內的優惠後，同群組其他資格均被排除。
- 「不可疊加 = `false`」的資格可在前一任務結案後再領取，但不得超過其 Business Day 有效期限。
- 不可疊加與 Exclusive Group 同時命中時，兩組排除規則均正確生效。

### 16.3 金額與流水

- 固定金額與儲值百分比 Bonus 均正確計算。
- 百分比 Bonus 不超過優惠最高金額。
- Bonus、每局有效流水、Required Wager Amount 及 Converted Amount 均直接截斷至小數第 4 位。
- `CurrentWagerAmount` 達標時正確回傳 `ReadyToClose` 且任務仍在進行中；只有 Host 另呼叫達標結案後才建立歷史及重置任務。
- DBCache 保證同一局最終遊戲資料僅送入一次，核心服務依結算後資料正確回傳任務結果。
- Fixed Convert 即使高於 Bonus Wallet 餘額或原始 Bonus，仍發放設定全額。
- Balance Convert 在設定上限非空時不超過該上限。

### 16.4 結案與維護

- 達標、Bonus 用盡、主動放棄及逾期失效均建立正確的 Bonus History。
- 結案時先建立歷史，再重置 Bonus Status 任務資料。
- 逾期維護能回傳正確的 Bonus Wallet 清空名單。
- Balance Convert 公式異常時，結案交易回復但已提交的達標流水保留，任務維持進行中且可重試結案。
- 超過 90 日的歷史資料由每日維護刪除。
- 每日維護重複呼叫或同時執行時，不重複建立歷史或重複變更玩家狀態。

### 16.5 資料存取

- 核心業務邏輯只依賴核心專用資料存取介面，不直接操作 `MysqlAcess` 的表名、欄位或 dictionary。
- 簡單新增、更新及查詢均使用 `MysqlAcess` 的參數化 API，不使用舊版 SQL 字串拼接方法。
- 領取優惠的玩家鎖定與所有狀態異動在同一資料庫交易中完成；任一步驟失敗時不留下部分成功資料。
- 多程序或多實例同時領取時，MySQL 資料列鎖仍能保證同一玩家只有一個要求成功。
- EventId 與活動 UID、BonusTaskId 等唯一索引能阻止資料庫重試或併發造成重複資料。
- 每日歷史清理使用參數化刪除或其他已擴充的安全參數化 API，不拼接外部輸入產生 SQL。

## 17. 已知且接受的風險

- 玩家可能透過 Bonus Wallet 歸零而提前結案，之後恢復提款資格並產生套利空間。
- 此風險已知且可接受，第一版不需增加額外限制或防套利機制。

## 18. 已確認業務規則

第一版採用下列已確認規則：

1. 儲值百分比僅供活動派發 Bonus 計算使用，且僅能搭配每日首儲或儲值觸發類型；其他觸發類型由 H5gSet 禁止此組合。
2. Host 為每次觸發事件提供全域唯一 EventId；核心服務重複收到相同 EventId 時，回傳首次處理結果且不重複建立資格。
3. 核心領取成功後，若 DBCache 派發 Bonus Wallet 失敗，核心狀態不回復；由 DBCache 使用相同 BonusTaskId 負責安全重試、避免重複入帳及錯誤處理。
4. 領取時保存完整活動設定快照，進行中的 Bonus Task 不受活動設定後續修改影響。
5. 達標時核心先回 `ReadyToClose`，由 DBCache Host 另呼叫達標結案，成功後再清空 Bonus Wallet；輸光時由 DBCache 確認結算後餘額歸零並另呼叫用盡結案；主動放棄時由核心服務成功結案後通知 DBCache 清空 Bonus Wallet。
6. 遊戲資料的重送、取消及退款由 DBCache 控管。DBCache 每局只將最終的押分、得分、遊戲時間及結算後 Bonus Wallet 餘額送入核心服務一次，核心服務計算流水後回傳任務結果。
7. 核心服務在領取時以玩家為單位上鎖。同一玩家的同時領取要求中，先取得鎖且通過驗證者成功。
8. 每日維護不要求 EventId，但維護操作本身必須具備 Idempotency，確保重複呼叫或同時執行不會重複產生業務結果。
