## 4. 共用名詞與引用規則

- 共用名詞、領域列舉、欄位與計算語意以 [PCS-01](./01_優惠活動資料模型與欄位定義.md) 為唯一基準。
- 資料庫 Transaction(交易)、唯一索引、玩家 Row Lock(資料列鎖)與固定鎖定順序引用 PCS-02。
- 資料層錯誤分類引用 PCS-03；本文件負責轉成 API Result 與 Host 行動。
- API 方法、Request、Result、Wallet Instruction(錢包指令)與 `OperationKey` 引用 PCS-04。
- 第一版維持 PCS-02 現有 Schema，不新增 Transactional Outbox(交易寄件匣)或遊戲局冪等表；因此本文件明確列出無法自動消除的回應遺失風險。

## 5. 錯誤模型

### 5.1 結果分類

所有公開方法使用 PCS-04 的 `PromotionResult<T>`，分類如下：

| Kind | 是否代表業務成功 | Data | Host 行動 |
|---|---:|---|---|
| `Succeeded` | 是 | 必填 | 可靠保存並執行 Wallet Instruction；無指令則完成 |
| `Rejected` | 否 | 通常為 null；安全診斷資料放在 ErrorDetails | 不自動重試；重新讀取狀態或提示玩家 |
| `RetryableFailure` | 否，且已確認未提交 | 可選 | 依本文件 Backoff 規則重試完整 API |
| `PermanentFailure` | 否 | 可選 | 修正輸入、設定、資料或程式後再處理 |
| `OutcomeUnknown` | 不確定 | 可含查證到的診斷狀態 | 禁止盲目重送；先查證及對帳 |
| `PartialSucceeded` | 部分是 | 必填 | 保存成功項目的指令；按失敗明細處理 |

### 5.2 不變條件

- `ErrorCode = None` 只允許搭配 `Succeeded`。
- `MaintenancePartiallySucceeded` 只允許搭配 `PartialSucceeded`。
- `IsRetryable = true` 只表示相同 Request 在指定條件下可以重試，不代表核心服務保證自動重試。
- `OutcomeUnknown` 的 `IsRetryable` 固定為 false；完成查證後才可能形成新的重試決策。
- 例外訊息、MySQL 錯誤文字與 Stack Trace(堆疊追蹤)不是 API 契約，不得由 Host 解析。
- 核心服務應攔截已知資料與業務例外並轉成 Result；`OutOfMemoryException`、`StackOverflowException` 等程序級致命錯誤不承諾轉換。
- ErrorDetails 只可使用 PCS-04 定義的結構化欄位；不得用自由文字夾帶資料庫或玩家敏感資訊。

## 7. 共通輸入錯誤

| ErrorCode | Kind | IsRetryable | 觸發條件 |
|---|---|---:|---|
| `ServiceNotInitialized` | `PermanentFailure` | false | 初始化完成前呼叫其他 API |
| `InitializationConflict` | `PermanentFailure` | false | 重複初始化使用不同切換時間或公式委派 |
| `RequestNull` | `PermanentFailure` | false | Request 為 null |
| `InvalidUserUID` | `PermanentFailure` | false | UserUID 小於或等於 0 |
| `InvalidIdentifier` | `PermanentFailure` | false | EventId、BonusTaskId、EligibilityEntryId 或 CorrelationId 格式錯誤 |
| `InvalidEnumValue` | `PermanentFailure` | false | 傳入未定義 enum 值 |
| `InvalidDateTime` | `PermanentFailure` | false | 時間範圍、Kind 或切換時間不合法 |
| `InvalidAmount` | `PermanentFailure` | false | 負數、精度超過 4 位或超過資料庫範圍 |
| `InvalidPaginationOrBatchSize` | `PermanentFailure` | false | Offset、Limit 或 BatchSize 超出 PCS-04 規則 |
| `InvalidActivityScope` | `PermanentFailure` | false | AllowedActivityUIDs 為 null 或含非法 UID |
| `InvalidEligibleDepositAmount` | `PermanentFailure` | false | 儲值事件缺少合格金額，或非儲值事件帶入金額 |
| `UnsupportedSnapshotVersion` | `PermanentFailure` | false | 任務或歷史使用核心不支援的快照版本 |
| `InvalidHistoryRange` | `PermanentFailure` | false | 歷史起訖不合法、跨度超過 90 日或結束時間晚於目前時間 |

輸入錯誤必須在可行範圍內於開啟交易前回傳；不得寫入資料或呼叫 Balance Convert(依餘額解鎖)公式。

## 8. 建立資格錯誤

| 情境 | 結果 |
|---|---|
| EventId 不存在且零活動符合 | `Succeeded`，空 Entries；不是錯誤 |
| 同玩家、同 Business Day 的第二個每日首登入／首儲 EventId | 保存 Event，`Succeeded`、`IsReplay = false`、空 Entries；不重新篩選活動 |
| 已保存較晚每日觸發日期後收到舊 Business Day 的新 EventId | 保存 Event，`Succeeded`、`IsReplay = false`、空 Entries；保存日期不得倒退 |
| EventId 已存在且首次輸入相同 | `Succeeded`、`IsReplay = true` |
| EventId 已存在但事件內容不同 | `Rejected / EventIdConflict` |
| AllowedActivityUIDs 為空 | `Succeeded`，建立零資格事件 |
| 活動範圍含不存在 UID | 忽略不存在的活動；不是錯誤 |
| 活動資料不符合 PCS-01 | `PermanentFailure / DataCorruption` |
| EventId 新增競爭造成主鍵重複 | 查回既有事件後依相同／衝突規則處理 |

`EventIdConflict` 可透過 ErrorDetails 回傳 EventId、首次事件的 UserUID、TriggerType、EventTime 與 BusinessDay，但不得回傳或寫入第二次要求的資料作為首次事實。

## 9. 領取優惠錯誤

| ErrorCode | Kind | IsRetryable | 說明 |
|---|---|---:|---|
| `EligibilityNotFound` | `Rejected` | false | 找不到指定資格 |
| `EligibilityPlayerMismatch` | `Rejected` | false | 資格不屬於 Request 玩家 |
| `EligibilityExpired` | `Rejected` | false | 資格已 Expired 或 Business Day 已過 |
| `EligibilityExcluded` | `Rejected` | false | 資格已 Excluded |
| `EligibilityAlreadyClaimed` | `Rejected` | false | 已領取但不是可安全重播的同一結果 |
| `ActiveBonusTaskExists` | `Rejected` | false | 玩家已有另一個進行中任務 |
| `DailyClaimLimitReached` | `Rejected` | false | 鎖定後重算已達每日領取上限 |
| `ActivityNotFound` | `PermanentFailure` | false | 指定活動不存在，或資格引用的活動設定不存在 |
| `ClaimReplayDataUnavailable` | `PermanentFailure` | false | 已領取任務不在目前狀態，且 90 日歷史已清除，無法重建派發資料 |

資格已 Claimed 且可從 Bonus Status 或 Bonus History 還原同一任務時，應回傳 `Succeeded` 與同一 Wallet Instruction，不回傳 `EligibilityAlreadyClaimed`。唯一鍵競爭必須先查證資料內容，不能將所有 Duplicate Key(重複鍵)都視為重播成功。

## 10. 任務與結案錯誤

| ErrorCode | Kind | IsRetryable | 說明 |
|---|---|---:|---|
| `BonusTaskNotFound` | `Rejected` | false | 玩家無目前任務，且查無 ExpectedBonusTaskId 歷史 |
| `BonusTaskMismatch` | `Rejected` | false | 玩家目前任務與 ExpectedBonusTaskId 不同 |
| `InvalidBonusTaskState` | `PermanentFailure` | false | 已提交狀態為 Closing 或欄位組合非法 |
| `BonusWalletNotDepleted` | `Rejected` | false | 獨立用盡通知的結算後餘額不等於 0 |
| `BalanceConvertFormulaFailed` | `RetryableFailure` | true | 公式擲出例外、回傳 NaN、無限值、負數或無法轉為 decimal |
| `WagerRequirementNotMet` | `Rejected` | false | Host 要求達標結案，但鎖定後的目前流水尚未達標 |

### 10.1 已結案重播

- ExpectedBonusTaskId 已有 Bonus History 時，結案 API 回傳 `Succeeded`、`AlreadyClosed = true` 及既有結案內容。
- 重送的要求類型不得覆寫既有 CloseReason；例如已因達標結案後收到放棄要求，仍回傳原 `WagerCompleted`。
- 若目前已是另一個任務，舊 ExpectedBonusTaskId 查有歷史時只回傳舊結果，不得異動新任務。
- 若查到同 BonusTaskId 的歷史內容與原任務可驗證欄位不一致，回傳 `DataIntegrityConflict`。

### 10.2 同局達標與歸零

`AccumulateWager` 套用本局有效流水後若同時達標且 `SettledBonusWalletBalance = 0`，仍只提交流水並回 `ReadyToClose`，不在累計交易內決定 CloseReason。Host 應優先呼叫 `CloseWagerCompletedBonusTask`：

| Convert Type | CloseReason | Converted Amount | 是否呼叫公式 |
|---|---|---:|---:|
| `Fixed` | `WagerCompleted` | Fixed Converted Amount | 否 |
| `Balance` | `WagerCompleted` | 依達標局結算後餘額計算 | 是 |

若 Host 在未達標但餘額為 0 時呼叫 `CloseDepletedBonusTask`，則以 `BonusDepleted` 結案。為保留既有防禦行為，`CloseDepletedBonusTask` 發現流水已達標時仍依 Convert Type 判定：`Fixed` 改為 `WagerCompleted`，`Balance` 維持 `BonusDepleted` 且不呼叫公式；正常 Host 流程不得用它取代達標結案方法。

### 10.3 公式失敗

- 公式在獨立結案交易內執行；任何公式失敗必須 Rollback 整筆結案交易，Bonus Status 保持 `InProgress`，已由先前 `AccumulateWager` 提交的達標流水不得回復。
- 不建立 Bonus History、不重置任務、不回傳 Wallet Instruction。
- 可用完全相同的 Request 重試；公式必須無副作用且輸入相同時產生相同結果。
- 連續失敗不是資料庫暫時性錯誤。核心服務不自動重試公式，由 Host 依營運政策重試並告警。

## 11. 每日維護錯誤

### 11.1 逐項隔離

- Eligibility Entry(可領活動項目)逾期、每位玩家的任務逾期及每批歷史刪除分別依 PCS-02 的交易邊界處理。
- 單一玩家失敗只 Rollback 該玩家；其他玩家繼續。
- 成功項目的計數及 Wallet Instruction 必須保留，失敗項目寫入 `MaintenanceFailureDto`。
- 有成功也有失敗時回傳 `PartialSucceeded / MaintenancePartiallySucceeded`；所有候選都失敗且沒有任何成功異動時，回傳第一個具代表性的失敗 Kind 與 ErrorCode，Data 仍可含完整失敗清單。
- 維護本身不會使用 Balance Convert 公式；逾期結案 Converted Amount 固定為 0。

### 11.2 重跑

- Host 重跑時必須使用原 `ExecutionTime`，維持相同 CurrentBusinessDay 與 HistoryCutoffTime；不得改成重試當下時間。
- 已 Expired、已結案或已清除的資料不再異動。
- 單筆任務 Commit 結果不明時，核心先以 BonusTaskId 查 Bonus History；存在且內容一致時列為成功。
- 第一版沒有維護執行識別碼或 Outbox。若整個成功回應在 Host 保存前遺失，重跑只能保證資料庫狀態不重複，不能重現上次已回傳的全部清空錢包清單；此情況進入第 17 節人工對帳。

## 12. 資料存取錯誤映射

| PromotionDataErrorKind | API 處理 | 預設 Result |
|---|---|---|
| `Validation` | 若是 API 輸入，映射對應 1xxx；若是 Adapter 命令建構錯誤，視為程式缺陷 | `PermanentFailure` |
| `DuplicateKey` | 依 ConstraintName 及第 12.1 節查證 | 成功重播、業務衝突或 `DataIntegrityConflict` |
| `ConcurrencyConflict` | Rollback 本次交易，以新交易重新讀取並判定當前資格／任務狀態；不可重送單條 Update，也不按 Duplicate Key 處理 | 依重新讀取的業務狀態回傳對應結果；若仍無法判定則 `PermanentFailure / DataIntegrityConflict` |
| `Deadlock` | Rollback 完整交易並依第 18 節重試 | 重試耗盡後 `RetryableFailure / DatabaseDeadlock` |
| `LockWaitTimeout` | Rollback 完整交易並依第 18 節重試 | 重試耗盡後 `RetryableFailure / DatabaseLockWaitTimeout` |
| `Connection` | 已確認尚未進入 Commit，或 Commit 結果不明但查證後可證明未提交時，由核心服務重試完整交易；無法證明時升級為結果不明 | 核心重試耗盡後為 `RetryableFailure / DatabaseConnectionFailure`；無法判定時為 `OutcomeUnknown / CommitOutcomeUnknown` |
| `CommitOutcomeUnknown` | 依業務識別碼查證，不直接重送 | 查證成功、可安全重試，或 `OutcomeUnknown / CommitOutcomeUnknown` |
| `DataCorruption` | 停止業務處理並告警 | `PermanentFailure / DataCorruption` |
| `Unexpected` | 記錄 CorrelationId 並停止 | `PermanentFailure / UnexpectedError` |

### 12.1 Duplicate Key 對照

| ConstraintName | 必要處理 |
|---|---|
| PromotionTriggerEvent PK(EventId) | 查回事件；輸入一致則重播，否則 `EventIdConflict` |
| `UK_EligibilityEntry_EventId_ActivityUID` | 查回同事件資格；一致才視為重播 |
| `UK_EligibilityEntry_ClaimedBonusTaskId` | 查回資格、Bonus Status／History；一致才視為成功 |
| `UK_PromotionBonusStatus_BonusTaskId` | 整筆 Rollback，產生新 Guid 後重做領取，最多 3 次 |
| `UK_PromotionBonusHistory_BonusTaskId` | 查回歷史；內容一致則回傳既有成功結果 |
| 其他或 ConstraintName 缺失 | `PermanentFailure / DataIntegrityConflict`，不得猜測為冪等成功 |

## 13. 可重試與不可重試分類

### 13.1 重試主體

1. 核心服務先處理單次 API 內的 Deadlock、Lock Wait Timeout，以及已確認未提交的 Connection Failure(連線失敗)重試。
2. 核心回傳 `RetryableFailure` 後，由 DBCache 重試完整公開 API；不得只重送最後一條 SQL 或直接呼叫 Repository。
3. Wallet Instruction 由 DBCache 以 OperationKey 重試；不得要求核心回復已 Commit 的領取或結案。

核心內部重試與 Host 重試是兩層獨立但有上限的保護：一次公開 API 呼叫內，核心最多嘗試 3 次完整交易；核心耗盡後，Host 才依第 13.2 節發起新的完整 API 呼叫。兩層嘗試次數都必須分別記錄，不得因換連線而將同一層計數歸零。

### 13.2 Host 重試政策

| ErrorCode | 最大 Host 嘗試次數 | Backoff | 必要條件 |
|---|---:|---|---|
| `DatabaseDeadlock` | 3 次 | 第 2、3 次前分別等待 100、300 ms，加 0～100 ms jitter | 原 Request 完全相同 |
| `DatabaseLockWaitTimeout` | 3 次 | 第 2、3 次前分別等待 250、750 ms，加 0～100 ms jitter | 原 Request 完全相同 |
| `DatabaseConnectionFailure` | 3 次 | 第 2、3 次前分別等待 500、1500 ms，加 0～250 ms jitter | 已確認交易未提交 |
| `BalanceConvertFormulaFailed` | 由營運政策決定，建議 3 次 | 第 2、3 次前分別等待 1、5 秒 | 原 Request 與同一已初始化公式委派；耗盡後告警 |

表中「最大嘗試次數」包含第一次 Host 呼叫。重試計數不得因程序內部換連線而歸零。

### 13.3 禁止自動重試

- 所有 `Rejected`、`PermanentFailure` 與 `OutcomeUnknown`。
- EventId 衝突、BonusTaskId 不符、資格終態及每日上限。
- `AccumulateWager` 的結果不明，因第一版沒有 GameRoundId 冪等紀錄。
- 每日維護成功回應遺失後，為取回 Wallet Instruction 而直接重跑；重跑不保證重現清單。
- 已 Commit 的領取或結案不得用補償交易回復核心狀態。

## 14. EventId 冪等性

### 14.1 比較欄位

EventId 首次處理事實由下列欄位構成：

- UserUID
- TriggerType
- EventTime
- 依 EventTime 算出的 BusinessDay
- EligibleDepositAmount

`AllowedActivityUIDs` 不屬於重送比較欄位；它只用於首次篩選。EventId 已存在時永遠讀取首次 Eligibility Entry 清單。

### 14.2 正規化與相等

- EventId 逐字元、區分大小寫比較，不 Trim、不轉換大小寫。
- EventTime 進入交易前截斷至 MySQL `DATETIME(6)` 可保存的微秒精度，再用同一值保存及比較。
- decimal 以數值相等比較，且輸入必須符合 4 位小數限制。
- null 只與 null 相等；不得把 null、0 或空字串視為相同。
- 首次零資格結果與非零結果具有相同冪等效力，均永久保留事件紀錄。

### 14.3 結果

| 狀態 | 行為 |
|---|---|
| 無既有事件 | 建立事件及資格，`IsReplay = false` |
| 有事件且內容相同 | 回傳原資格清單，`IsReplay = true` |
| 有事件且內容不同 | `Rejected / EventIdConflict` |
| 新增時唯一鍵競爭 | 回到既有事件比較流程，不直接報資料庫錯誤 |

---

## 15. BonusTaskId 冪等性

### 15.1 領取

- BonusTaskId 由核心服務在領取交易內產生；DBCache 不得自行指定。
- 領取成功後，Eligibility Entry 的 `ClaimedBonusTaskId`、Bonus Status 及 Wallet Instruction 使用同一值。
- Claim 重播可還原資料時，回傳相同 BonusTaskId 及 `{BonusTaskId}:CreditBonusWallet`。
- Guid 唯一鍵碰撞必須 Rollback 後使用新值重做，不得把碰撞的其他任務當成自己的成功結果。

### 15.2 任務異動

- `AccumulateWager`、`CloseWagerCompletedBonusTask`、`CloseDepletedBonusTask` 與 `AbandonBonusTask` 都必須傳入 ExpectedBonusTaskId。
- 鎖定玩家後必須重新比較；不符時回傳 `BonusTaskMismatch`，禁止更新目前新任務。
- `AccumulateWager` 對「每局」不是冪等操作。BonusTaskId 只能避免舊任務要求打到新任務，不能防止同一局對同任務重複累加。

### 15.3 結案

- `UK_PromotionBonusHistory_BonusTaskId` 保證每個任務最多一筆歷史。
- 結案重送先查 History；存在且內容一致時回傳原結果與相同 Wallet Instructions。
- Wallet OperationKey 固定由 BonusTaskId 與 WalletAction 組成，讓 DBCache 對派發、清空與轉入主錢包分別冪等。
- Bonus History 超過 90 日清理後，不再保證可透過核心 API 重現舊結案結果；DBCache 必須保存已執行 Wallet Operation 的紀錄至少符合自身對帳期限。

## 16. Commit 結果不明

### 16.1 共通流程

當 Connection 在 Commit 前後中斷，且 Driver 無法證明 Commit 成功或失敗時：

1. `ExecuteInTransaction` 不得在原交易 Context 內再次執行 action；若後續查證可證明未提交，只能由核心服務上層重新建立連線與完整交易。
2. 關閉不可用連線，以新連線進行唯讀查證。
3. 只使用 EventId、EligibilityEntryId、ExpectedBonusTaskId、Bonus History 及目前狀態判斷。
4. 查證到唯一且內容一致的成功證據時，回傳 `Succeeded`／既有結果。
5. 查證到明確未提交狀態時，由核心服務先依第 18 節重試完整交易；核心重試耗盡才回傳 `RetryableFailure / DatabaseConnectionFailure`，允許 Host 重試完整 API。
6. 查證本身失敗、證據不唯一或操作本質無法去重時，回傳 `OutcomeUnknown / CommitOutcomeUnknown`。

### 16.2 各 API 查證

| API | 成功證據 | 明確未提交 | 無法判定時 |
|---|---|---|---|
| `CreateEligibility` | EventId 存在、首次內容一致，且資格清單可讀 | EventId 不存在；核心重試，耗盡後回傳 `DatabaseConnectionFailure` | `OutcomeUnknown` |
| `ClaimPromotion` | 資格為 Claimed，且 Bonus Status 或 History 可還原同 BonusTaskId | 資格仍 Available 且玩家無任務；核心重試，耗盡後回傳 `DatabaseConnectionFailure` | `OutcomeUnknown` |
| `AccumulateWager` | 無充分的逐局唯一證據 | 只有在錯誤明確發生於 Commit 前，且交易已 Rollback 時才可由核心重試 | Commit 開始後發生連線錯誤時一律 `OutcomeUnknown`，禁止重送該局 |
| `CloseWagerCompletedBonusTask` | 同 BonusTaskId History 存在且一致 | 同任務仍 InProgress 且查證完成；核心重試，耗盡後回傳 `DatabaseConnectionFailure` | `OutcomeUnknown` |
| `CloseDepletedBonusTask` | 同 BonusTaskId History 存在且一致 | 同任務仍 InProgress 且查證完成；核心重試，耗盡後回傳 `DatabaseConnectionFailure` | `OutcomeUnknown` |
| `AbandonBonusTask` | 同 BonusTaskId History 存在且一致 | 同任務仍 InProgress 且查證完成；核心重試，耗盡後回傳 `DatabaseConnectionFailure` | `OutcomeUnknown` |
| 單一逾期任務 | 同 BonusTaskId History 存在且 CloseReason 正確 | 同任務仍 InProgress | 該玩家列入維護失敗 |
| 歷史刪除 | 不需要重複產生業務結果；可重跑相同 cutoff | 符合條件資料仍存在 | 查證失敗則維護失敗 |

### 16.3 `AccumulateWager` 特別限制

第一版由 DBCache 保證每局只送一次，核心資料庫沒有 GameRoundId。Commit 結果不明時，即使查到 Current Wager Amount 增加，也不能證明是本局或另一局造成；即使查到歷史，也不能完整證明本局是否已納入最終流水。因此：

- 不得自動或人工以相同 Request 再次送入核心。
- 應暫停該玩家後續優惠遊戲處理，保存本局原始最終資料。
- 以 DBCache 遊戲紀錄、核心 Bonus Status／History 與資料庫日誌人工對帳。
- 對帳完成前不得自行更改核心資料表。

## 17. DBCache 錢包一致性

### 17.1 一致性邊界

核心資料庫與 DBCache 錢包不在同一 Transaction。第一版也沒有 Outbox，因此提供的是「核心先 Commit、Host 再依冪等鍵處理錢包」的最終一致性，不是原子一致性。

```text
核心交易 Commit
    ↓
API 回傳 Wallet Instructions
    ↓
DBCache 可靠保存指令
    ↓
依 OperationKey 冪等執行錢包
    ↓
記錄完成
```

### 17.2 指令順序

| 業務結果 | Wallet Action 順序 |
|---|---|
| 領取成功 | `CreditBonusWallet` |
| WagerCompleted | `ClearBonusWallet`，再執行 `CreditMainWallet` |
| BonusDepleted | 無；Host 已確認餘額為 0 |
| PlayerAbandoned | `ClearBonusWallet` |
| BusinessDayExpired | `ClearBonusWallet` |

- 同一 OperationKey 執行多次必須只生效一次。
- `CreditMainWallet` 不得早於同任務的 `ClearBonusWallet` 完成。
- 單一指令失敗時只重試該錢包指令，不重新呼叫已成功的核心領取或結案 API。
- 核心成功但錢包失敗時，不回復 Eligibility Entry、Bonus Status、Bonus History、領取次數或排除結果。
- Bonus 派發完成前不得開放任務遊玩；結案的所有必要指令完成前，DBCache 必須維持適當的提款／任務流程限制。

### 17.3 回應遺失與已接受風險

下列 Crash Window(當機時間窗)在第一版無法由現有 Schema 自動消除：核心 Commit 已成功，但 API 回應在 DBCache 可靠保存 Wallet Instruction 前遺失。

- 領取與單一結案可優先重呼叫相同業務 API，由 BonusTaskId／History 嘗試重現指令；只有查證到既有成功時才能執行。
- `AccumulateWager` 不得重呼叫；依第 16.3 節對帳。
- 每日維護整體回應遺失時，重跑不保證重新列出已結案玩家；必須從該次維護時間窗內的 Bonus History、DBCache 錢包紀錄與應用程式日誌對帳。
- 若 Bonus History 已被清理，核心可能無法重建舊指令；DBCache 的 Wallet Operation 紀錄必須獨立保存。
- 對帳只能補執行具相同 OperationKey 的錢包操作，不得直接修改核心資料或建立第二筆歷史。

此風險是第一版明確接受的架構限制。若後續要求自動保證不遺失，必須先在 PCS-01～PCS-03 新增 Outbox Schema、狀態、索引與消費契約，再修改本文件；不能只靠增加 API 重試次數達成。

## 18. Deadlock、Lock Wait Timeout 與連線失敗重試

### 18.1 核心內部重試

- Deadlock 或 Lock Wait Timeout 每次都 Rollback 整筆 Transaction；確認未提交的 Connection Failure 則關閉不可用連線。兩者都必須重新建立交易並重新讀取所有資料。
- 最大 3 次核心嘗試，包含第一次執行。
- Deadlock 與 Lock Wait Timeout 的 Backoff：第 2 次前 25 ms、第 3 次前 100 ms，各加 0～25 ms jitter(抖動)。
- 確認未提交的 Connection Failure Backoff：第 2 次前 100 ms、第 3 次前 300 ms，各加 0～100 ms jitter。
- 使用相同 EventId、ExpectedBonusTaskId、Request 時間與金額；不得重算 Host 輸入。
- 領取交易第一次尚未 Commit 時，重試可重新產生 BonusTaskId；只有成功 Commit 的 BonusTaskId 對外可見。
- Balance Convert 公式可能因完整交易重試而再次執行，故必須決定性且無副作用。
- `AccumulateWager` 只有在錯誤明確發生於 Commit 前且已完成 Rollback 時適用本節；一旦進入 Commit 後結果不明，立即依第 16.3 節停止重試。

### 18.2 重試耗盡

- 最後錯誤為 Deadlock 時回傳 `RetryableFailure / DatabaseDeadlock`。
- 最後錯誤為 Lock Wait Timeout 時回傳 `RetryableFailure / DatabaseLockWaitTimeout`。
- 最後錯誤為已確認未提交的 Connection Failure 時回傳 `RetryableFailure / DatabaseConnectionFailure`。
- Result 的 CorrelationId 保持不變，並記錄每次內部嘗試編號。
- Host 再依第 13 節重試完整 API；每次仍須重新讀取，不得傳回或重用交易 Context。

### 18.3 降低衝突

- 嚴格遵守 PCS-02：PromotionBonusStatus → PromotionTriggerEvent → EligibilityEntry → PromotionActivity → PromotionBonusHistory。
- 多玩家依 UserUID 遞增；同玩家多資格依 EligibilityEntryId 遞增。
- 不在取得玩家鎖前執行會影響後續寫入判斷的非交易查詢。
- 不因 Deadlock 而放寬唯一索引、狀態條件或鎖定範圍。

## 19. 日誌與稽核

### 19.1 每次 API 必記欄位

- API 名稱、DLL 版本及 SnapshotVersion。
- CorrelationId。
- 開始／結束本地時間、耗時及結果 Kind。
- PromotionErrorCode、`IsRetryable`、內部重試次數。
- 遮罩後的 UserUID、EventId、EligibilityEntryId、BonusTaskId。
- Commit 狀態：未開始、已 Rollback、已 Commit、結果不明、查證結果。
- Wallet Instruction 的 Action、OperationKey 雜湊及 Amount；不得記錄錢包憑證。
- 維護的 CurrentBusinessDay、HistoryCutoffTime、批次編號、成功／失敗計數。

### 19.2 事件特定欄位

| 情境 | 額外紀錄 |
|---|---|
| EventId 衝突 | 哪些欄位不同；值依遮罩政策處理 |
| Deadlock／Lock Wait | 嘗試次數、MySQL 錯誤碼、交易階段，不記錄完整 SQL 參數 |
| Commit 結果不明 | 原操作、查證查詢結果及最終人工案件識別碼 |
| 公式失敗 | 委派型別與方法名稱、例外型別或非法結果類別，不記錄完整快照 |
| 資料損毀 | 表、主鍵遮罩、違反的欄位組合或 SnapshotVersion |
| 維護部分成功 | 每筆失敗的 Stage、UserUID、BonusTaskId 與 ErrorCode |

### 19.3 禁止記錄

- 資料庫連線字串、密碼、Token(權杖)或錢包授權資料。
- 完整 Activity Snapshot JSON。
- 可直接識別玩家的未遮罩個人資料。
- 將參數值串回成可執行 SQL。
- Balance Convert Context 的完整內容；需要除錯時只記錄經批准的欄位及雜湊。

日誌不取代 Promotion Trigger Event、Eligibility Entry、Bonus History 或 DBCache Wallet Operation 的正式稽核資料。
