## 4. 共用名詞與引用規則

- 共用名詞、列舉值、欄位語意、精度及計算式以 [PCS-01](./01_優惠活動資料模型與欄位定義.md) 為唯一基準。
- Schema、唯一索引、Transaction(交易)邊界、Row Lock(資料列鎖)及固定鎖定順序以 PCS-02 為準。
- Repository(資料存取庫)、Adapter(轉接器)、MysqlAcess 擴充及資料例外分類以 PCS-03 為準。
- API Request、Result、DTO(Data Transfer Object，資料傳輸物件)與 Wallet Instruction(錢包指令)以 PCS-04 為準。
- 錯誤碼、重試、冪等性及 Commit Outcome Unknown(提交結果不明)以 PCS-05 為準。
- 本文件只定義驗證方式，不得新增或改寫上游業務規則。若測試無法由 PCS-01～PCS-05 得出唯一預期，必須先修訂上游文件，再新增測試。
- 每個測試使用本文件的唯一案例編號，測試名稱格式為「案例編號_條件_預期」，並以 Trait 標示來源文件及測試層級。
- 表格中的每一列是獨立可執行案例；使用資料驅動測試時，每組資料仍須在測試輸出中顯示案例編號或資料列名稱。
- 除特別標為人工演練的 Crash Window(當機時間窗)外，本文件案例均為第一版交付必要案例。

## 5. 測試層級、工具與執行環境

### 5.1 測試層級

| 層級 | System Under Test(受測系統) | 允許替身 | 禁止事項 |
|---|---|---|---|
| Unit Test(單元測試) | Business Day、Validator、Calculator、狀態轉換、Facade 協調邏輯 | 固定時鐘、記憶體 Data Store、手寫 Fake、可控公式 | 連線真實 MySQL、依賴系統現在時間、睡眠等待 |
| Contract Test(契約測試) | 公開 Facade、Result 不變條件、DTO、Host 錢包協作 | Fake Data Store、Fake Wallet、Fault Injector | 解析例外文字判斷結果 |
| Integration Test(整合測試) | MySQL Adapter、MysqlAcess V2、Schema、交易、唯一鍵、Row Lock | 只允許固定時鐘及 Fault Injection(故障注入) | 以 SQLite、記憶體資料庫或 Mock 取代 MySQL |
| Concurrency Test(併發測試) | 兩個以上獨立 Data Store／連線／Facade 執行個體 | Barrier(同步閘門)、可控鎖等待 | 只用同一連線或單一程序內 Mutex 模擬跨程序 |

單元測試與 Contract Test 不驗證 SQL；整合與 Concurrency Test 必須使用真實 InnoDB。相同規則可在不同層級重複驗證，但案例編號不可重複。

### 5.2 工具基準

- 測試框架使用 xUnit(測試框架)，目標框架固定為 .NET 6。
- 測試執行使用 Microsoft.NET.Test.Sdk；覆蓋率可使用 coverlet.collector。套件版本由實作時的集中套件鎖定管理，本文件不綁定修補版。
- 斷言優先使用 xUnit 原生 Assert；若導入第三方斷言套件，必須先確認授權及在 PCS-07 固定版本。
- MySQL Driver(驅動程式)必須與正式 Adapter 使用相同實作及版本，不得為測試另換 Provider。
- 測試不連接共用開發資料庫、正式資料庫或含真實玩家資料的環境。

### 5.3 MySQL 測試環境與隔離

- CI 使用與目標部署相同 Major／Minor 版本的 MySQL；Storage Engine 固定 InnoDB，Character Set 使用 utf8mb4，Collation 使用 utf8mb4_bin。
- 每個測試工作程序使用獨立資料庫；資料庫名稱由固定前綴、執行識別碼及工作程序編號組成，不含外部輸入。
- 套用正式 Migration 後才執行整合測試；測試不得自行建立較寬鬆的替代 Schema。
- 一般整合測試每案例清空資料表並重設自動編號。Concurrency Test 不可用外層測試 Transaction 包住案例，避免隱藏真實 Commit、Rollback 與 Row Lock 行為。
- 測試結束後刪除該次專用資料庫；失敗時先輸出診斷，再依 CI 保留政策清除。
- 涉及玩家併發的兩個執行端必須各自建立 MysqlAcess、連線與 Facade，證明一致性不是來自同一程序內 Mutex。

### 5.4 可控相依與故障注入

測試專用組合根至少提供：

- FixedLocalClock：每個 API 呼叫可設定唯一操作時間，並記錄 GetNow 呼叫次數。
- SequenceGuidProvider：依序提供 Guid，供碰撞及重試測試；正式實作仍使用安全的 Guid 來源。
- RecordingDelayProvider：記錄 Backoff 次數與範圍，不做真實睡眠。
- ScriptedBalanceConvertFormula：可回傳指定 double、擲出例外並記錄輸入及呼叫次數。
- ScriptedPromotionDataStore：可在 Begin、Command、BeforeCommit、DuringCommit、AfterCommit 階段注入錯誤。
- IdempotentWalletFake：依 OperationKey 保存及執行指令，可注入單一 Wallet Action 失敗。

測試 Hook 不得出現在公開 API，不得在正式組態啟用，也不得改變正式交易順序。

## 6. 測試資料建構規則

### 6.1 固定基準

除案例另有說明，使用下列基準：

| 資料 | 基準值 |
|---|---|
| BusinessDayCutover | 08:00:00 |
| 操作時間 | 2026-09-15 10:00:00.123456，本地時間且 Kind 為 Unspecified |
| CurrentBusinessDay | 2026-09-15 |
| UserUID | 10001 起，每案例不得共用 |
| ActivityUID | 20001 起，依排序需要配置 |
| EventId | evt-加案例編號，逐字元保留大小寫 |
| BonusTaskId | 合法小寫 D 格式 Guid，由 SequenceGuidProvider 供應 |
| Activity Snapshot | SnapshotVersion 1，CapturedAt 等於 Claim 操作時間 |
| 活動日期 | StartDate 為 2026-09-01；EndDate 為 2026-10-01 |
| WeekdayMask | 1111111 |
| ActivityStatus | Active（1） |
| Fixed Bonus | 10 |
| Deposit Percentage | 30；Max Bonus 為 100 |
| WagerMultiplier | 30 |
| WagerContributionRate | 100.0000 |
| Convert Type | Fixed；FixedConvertedAmount 為 5 |
| DailyClaimLimit | 1 |

每個 Builder(建構器)必須產生完整且合法的預設模型，案例只覆寫與條件直接相關的欄位。不得因 Builder 漏填欄位而讓測試意外驗證另一個錯誤。

### 6.2 時間邊界

- 切換前一微秒使用 07:59:59.999999；切換點使用 08:00:00.000000。
- StartDate 採包含邊界；EndDate 採不包含邊界。
- HistoryCutoffTime 等於 ExecutionTime 減 90 日；只有 ClosedAt 小於界線才可刪除。
- EventTime 儲存及比較前截斷至 MySQL DATETIME(6) 可保存精度。
- 不以 DateTime.Now、DateTime.Today 或資料庫 NOW 函式建立預期值。

### 6.3 金額與精度邊界

- 必測 0、最小合法正值、四位小數、第五位會被截斷的中間結果、上限剛好相等及超過上限。
- Request 金額超過四位小數是輸入錯誤；計算中間值可以超過四位，最終依 PCS-01 截斷。
- 整數活動設定的預期值使用 `int`；實際任務金額、流水及計算結果使用 decimal 常值建立且不經 double；只有 Balance Convert Formula 回傳值使用 double。
- 驗證「截斷」時至少包含第五位為 4 與 9 的資料，證明沒有四捨五入。

### 6.4 資料庫損毀資料

只有 DataCorruption 測試可繞過 Adapter，以資料庫管理連線直接植入未知 enum、非法欄位組合或非法 JSON。案例結束後不得把該方法重用於正常 Arrange；測試名稱及日誌必須明確標示為損毀資料注入。

## 10. API 契約測試

### 10.1 共通 Result 與初始化

| 案例編號 | 條件 | 必要斷言 |
|---|---|---|
| API-001 | 第一次以合法切換時間及公式初始化 | Succeeded、ErrorCode None、Data 必填、WasAlreadyInitialized false |
| API-002 | 相同切換時間及同一委派實例重複初始化 | Succeeded、WasAlreadyInitialized true，既有設定不變 |
| API-003 | 不同切換時間或不同委派實例重新初始化 | PermanentFailure／InitializationConflict |
| API-004 | 初始化前呼叫其餘十個 API | 各自回傳 PermanentFailure／ServiceNotInitialized，不存取資料庫 |
| API-005 | 多執行緒同時以相同設定初始化 | 只有一次建立設定，其餘皆為 AlreadyInitialized，無競態例外 |
| API-006 | 多執行緒同時以不同設定初始化 | 只有一組成功固定，其餘為 InitializationConflict，不出現混合設定 |
| API-007 | CorrelationId 為 null | 核心產生合法 Guid 字串；內部重試及結果沿用同一值 |
| API-008 | 合法 CorrelationId | 原樣回傳，不 Trim、不轉換大小寫 |
| API-009 | 任一 Succeeded／PartialSucceeded／失敗結果 | 分別驗證 PCS-04 5.3 的 Kind、ErrorCode、Data、ErrorDetails 及 IsRetryable 不變條件 |
| API-010 | 同一次 API 寫入多個時間欄位及 DTO | FixedLocalClock 只取一次 Now，所有操作時間一致 |

### 10.2 共通輸入驗證

下列案例使用資料驅動方式套用所有具有對應參數的公開 API，並斷言驗證失敗時不開交易、不呼叫公式、不產生 Wallet Instruction。

| 案例編號 | 非法輸入 | 預期錯誤碼 |
|---|---|---|
| VAL-001 | Request 為 null | RequestNull |
| VAL-002 | UserUID 小於或等於 0 | InvalidUserUID |
| VAL-003 | EligibilityEntryId 非正數；EventId 為空、超長或前後空白；BonusTaskId 非 D 格式；CorrelationId 為空或超長 | InvalidIdentifier |
| VAL-004 | 未定義 TriggerType 或其他公開 enum | InvalidEnumValue |

## 17. Deadlock、逾時、連線失敗與 Commit 結果不明測試

### 17.1 錯誤碼與重試分類

ERR-001 為資料驅動測試，逐一列舉 PCS-05 的 PromotionErrorCode，驗證固定數值、對外 PCS-四位數格式、ResultKind 及 IsRetryable。至少另有下列案例：

| 案例編號 | 條件 | 必要斷言 |
|---|---|---|
| ERR-002 | 未知 DuplicateKey ConstraintName | PermanentFailure／DataIntegrityConflict，不猜成重播 |
| ERR-003 | Adapter DataCorruption | PermanentFailure／DataCorruption，立即停止且告警 |
| ERR-004 | 非預期可攔截例外 | PermanentFailure／UnexpectedError，不洩漏例外文字或 Stack Trace |
| ERR-005 | ErrorDetails | 只含 PCS-04 定義欄位；一般資料庫錯誤為 null |

### 17.2 核心內部完整交易重試

| 案例編號 | 條件 | 必要斷言 |
|---|---|---|
| RTY-001 | 前兩次 Deadlock、第三次成功 | 每次完整 Rollback 並重新讀取；總嘗試 3；最終 Succeeded |
| RTY-002 | 三次皆 Deadlock | RetryableFailure／DatabaseDeadlock；核心嘗試數 3 |
| RTY-003 | 前兩次 Lock Wait Timeout、第三次成功 | 完整交易重做；Backoff 符合 25、100 ms 加合法 jitter |
| RTY-004 | 三次皆 Lock Wait Timeout | RetryableFailure／DatabaseLockWaitTimeout |
| RTY-005 | 連線錯誤明確發生於 Commit 前，前兩次失敗、第三次成功 | 關閉壞連線、重新建立完整交易；Backoff 符合 100、300 ms 加合法 jitter |
| RTY-006 | 已查證明確未提交的連線錯誤連續三次 | RetryableFailure／DatabaseConnectionFailure，交由 Host 決定外層重試 |
| RTY-007 | 內部重試 | Request、EventId、ExpectedBonusTaskId、時間、金額及 CorrelationId 不變；不得沿用舊模型或 Context |
| RTY-008 | Claim 重試前 Guid 尚未提交 | 可換新 Guid；只有最終 Commit 的 BonusTaskId 對外可見 |
| RTY-009 | Balance 結案因 Deadlock 重試 | 決定性公式可能被呼叫多次，每次 Context 相同且無副作用 |
| RTY-010 | Host 收到 RetryableFailure 後重試 | 重呼完整公開 API，不直接呼叫 Repository；Host 次數與核心次數分開記錄 |

### 17.3 Commit 結果不明查證

| 案例編號 | API／查證結果 | 必要斷言 |
|---|---|---|
| UNK-001 | CreateEligibility：Event 與完整 Entries 已存在且一致 | 還原 Succeeded；不得再執行交易 |
| UNK-002 | CreateEligibility：Event 不存在 | 判定未提交，核心建立新連線重試；耗盡才回 DatabaseConnectionFailure |
| UNK-003 | Claim：Entry Claimed 且 Status／History 可還原 | 還原相同 Succeeded 及 Wallet Instruction |
| UNK-004 | Claim：Entry Available 且玩家無任務 | 判定未提交並由核心重試；耗盡才交 Host |
| UNK-005 | Close／Abandon：History 存在且一致 | 還原既有成功結果，不重做結案 |
| UNK-006 | Close／Abandon：同任務仍 InProgress 且查證完整 | 判定未提交並由核心重試 |
| UNK-007 | AccumulateWager 在 Commit 前明確錯誤且已 Rollback | 核心可依 RTY 規則重試 |
| UNK-008 | AccumulateWager 進入 Commit 後斷線 | 無論讀到 Current 或 History 為何，一律 OutcomeUnknown／CommitOutcomeUnknown，不重送 |
| UNK-009 | 查證查詢本身失敗或成功證據不完整 | OutcomeUnknown／CommitOutcomeUnknown、IsRetryable false |
| UNK-010 | OutcomeUnknown | 不產生可直接執行的新 Wallet Instruction；日誌標示結果不明及查證結果 |
| UNK-011 | Delete History Commit 不明 | 以相同 cutoff 重新查證／重跑刪除，不產生業務 Wallet 結果 |

### 17.4 真實併發與鎖定

- CON-001：兩連線反向操作測試資料，證明 Deadlock 被穩定分類且整筆交易 Rollback。
- CON-002：一連線持有玩家 Row Lock，另一連線達到測試用 Lock Wait Timeout，證明未越過鎖更新資料。
- CON-003：壓力執行同玩家 Claim、CreateEligibility 與 Maintenance 的允許組合，資料庫最終滿足所有唯一鍵與狀態不變條件。
- CON-004：不同 UserUID 的交易可並行，不被全域業務鎖序列化；同一 MysqlAcess 實例的共用連線仍由程序內 Mutex 保護。

## 19. 測試執行與失敗診斷

### 19.1 執行分組

- Pull Request(合併請求)：全部 Unit Test、Contract Test、一般 Integration Test 各執行一次。
- 主分支：加跑所有 Concurrency Test，每個併發案例使用不同資料識別碼連續執行 50 回。
- 夜間測試：併發案例連續執行 500 回，並輪替至少兩組執行緒排程種子；任一失敗即不通過。
- 發布候選版：使用目標部署 MySQL 版本重新建立全新資料庫，從 Migration 開始跑完整測試。

不得以重跑後通過掩蓋 Flaky Test(不穩定測試)。第一次失敗即保存證據並建立缺陷；修正根因後才能恢復 Gate。

### 19.2 診斷輸出

失敗時輸出下列資料，且遵守 PCS-05 日誌遮罩：

- 案例編號、隨機種子、工作程序與執行回次。
- API 名稱、CorrelationId、Result Kind、ErrorCode、IsRetryable。
- FixedLocalClock、BusinessDay、Cutoff、輸入識別碼的遮罩值。
- 核心與 Host 嘗試次數、Fault Injection 階段、交易狀態及查證分支。
- 涉及資料列的主鍵、狀態及欄位差異；不得輸出完整 Activity Snapshot、密碼或可執行 SQL。
- 併發案例各執行端的 Barrier 到達順序、連線識別碼、鎖取得及 Commit／Rollback 順序。
- Wallet 指令的 Action、OperationKey 雜湊、順序及執行次數。

### 19.3 測試後殘留檢查

每個異動案例結束時至少驗證：

- 無未結束 Transaction、未釋放 Connection 或仍有效的 Transaction Context。
- 失敗案例沒有孤兒 Trigger Event、部分 Eligibility、半完成 Bonus Status 或重複 History。
- TaskState Closing 不得在 Commit 後殘留。
- Wallet Fake 沒有未在預期清單中的 OperationKey。
- 測試資料庫中每個唯一鍵及外鍵仍成立。

## 20. 完成標準

PCS-06 驗收完成必須同時符合：

- 本文件所有必要案例已轉成可執行測試，測試程式名稱可反查案例編號與來源文件。
- Unit、Contract、Integration 及 Concurrency Test 全數通過；沒有 Skip、暫時 Ignore 或只記錄不斷言的必要案例。
- 企劃第 16 節每項情境均由第 18 節追蹤到至少一個測試。
- 目標 MySQL 版本的全新 Migration 驗證通過。
- 主分支 50 回及夜間 500 回併發測試為零失敗、零重複任務、零重複歷史及零部分交易殘留。
- Fault Injection 已覆蓋 BeforeCommit、DuringCommit、AfterCommitBeforeReturn，以及查證成功、明確未提交與仍無法判定三條分支。
- 核心內部 Deadlock、Lock Wait Timeout、明確未提交的 Connection Failure 均最多嘗試 3 次；耗盡後 Result 正確。
- AccumulateWager 在 Commit 結果不明時，核心與 Host 均未重送該局。
- 所有 Wallet Instruction 先可靠保存再執行，OperationKey 重送不重複入帳。
- 測試輸出不含連線字串、密碼、完整 Snapshot、未遮罩玩家資料或可執行 SQL。
- 測試關閉後沒有連線、交易、Mutex 或測試資料庫資源洩漏。
